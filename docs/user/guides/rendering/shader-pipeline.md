# Shader Pipeline — Development & Compilation

UzEngine's shader pipeline is designed for rapid iteration during development and efficient pre-compilation for shipping builds.

> **Related**: [Spec 1.5.0 — Shader Pipeline Architecture](../../../specs/1.5.0-shader-pipeline.md) |
> [Shader VFS API](#shader-vfs) | [Hot-Reload System](#hot-reload-development)

## Overview

The shader pipeline solves a critical problem from engine development experience: **stale shader caches during rapid iteration**. By using content-based hashing (xxHash64) instead of timestamps, we ensure that changing a shader or any of its includes immediately invalidates the cache and recompiles.

### Two Modes

| Mode | Purpose | Behavior |
|------|---------|----------|
| **Development (`UZ_SHADER_DEV`)** | Rapid iteration, debugging | Load from disk, parse includes, compile on-demand, hot-reload on file change |
| **Shipping (`UZ_SHADER_SHIP`)** | Runtime performance | Load from precompiled archive, zero disk I/O for sources |

---

## Development Mode (UZ_SHADER_DEV)

In development builds, shaders are loaded from source files, compiled on-demand, and automatically recompiled when changed.

### Directory Layout

```
project/
├── shaders/
│   ├── engine/
│   │   ├── common.hlsli
│   │   ├── pbr.hlsl
│   │   └── gbuffer.hlsl
│   └── game/
│       └── custom.hlsl
└── cache/
    └── shaders/                          # Generated by compiler
        ├── dx12_sm66/
        │   ├── manifest.json
        │   └── <hash>.dxil
        ├── dx12_sm5/
        │   └── ...
        └── vulkan/
            └── ...
```

Shader source files are never committed to cache/ — that directory is generated locally during development.

### Shader Virtual File System (VFS)

All shader loading goes through the virtual filesystem. Modules mount their shader directories at startup:

```cpp
#include "core/shader/shader_vfs.h"

ShaderVFS vfs;
vfs.Mount("/engine", "shaders/engine");  // Built-in shaders
vfs.Mount("/game", "shaders/game");      // Game-specific shaders
```

Virtual paths resolve through mounts in reverse order (last mount wins), allowing overrides:

```cpp
// Default shader
vfs.Mount("/engine", "shaders/engine/pbr.hlsl");

// Game mod: override with custom PBR
vfs.Mount("/engine", "shaders/mod/pbr.hlsl");  // Takes priority
```

**Why virtual paths?**
- Decouples shader source location from code that references them
- Plugins can register shaders without hardcoding paths
- Enables mod systems: override engine shaders with game-specific versions

### Source Loading & Include Resolution

When you reference a shader, the system:

1. **Loads source** via VFS: `LoadSource("/engine/pbr.hlsl")`
2. **Parses `#include` directives** recursively (max depth 32)
3. **Resolves includes** through VFS, supporting both absolute and relative paths
4. **Deduplicates** includes (prevents double-compilation of common.hlsli)
5. **Computes content hash** over source + all includes + defines + target backend

Example shader with includes:

```hlsl
// pbr.hlsl
#include "common.hlsli"     // Virtual path relative to pbr.hlsl's dir
#include "../common/math.hlsli"  // Relative up-directory

cbuffer PerFrame : register(b0) {
    float4x4 viewProj;
    float3 cameraPos;
};

// ... shader code ...
```

**Include resolution flow:**
```
#include "common.hlsli"
  ↓
Relative to including file's directory
  ↓
Resolve "/engine/common.hlsli"
  ↓
Check ShaderVFS mounts
  ↓
Load from "shaders/engine/common.hlsli"
```

### Content-Based Identity (xxHash64)

Every shader is identified by a 64-bit content hash:

```
hash = xxHash64(
    source_content           // Root .hlsl file bytes
  + sorted(include_contents) // All transitive includes, sorted by path
  + compile_defines          // Permutation flags (e.g., "HAS_NORMAL_MAP=1")
  + target_backend           // "dx12_sm66", "vulkan", "metal"
  + compiler_version         // DXC version string (auto-update on DXC upgrade)
)
```

**Benefits:**
- No timestamps (works across machines, doesn't stale when clocks skew)
- No filenames in hash (moving files doesn't invalidate cache)
- Include changes propagate automatically (no manual invalidation)
- Deterministic (identical source always produces same hash)

**Example:**
```cpp
// Shader 1: Original
uint64_t hash1 = GetShaderHash("/engine/pbr.hlsl");  // a1b2c3d4...

// Modify common.hlsli (which pbr.hlsl includes)
uint64_t hash2 = GetShaderHash("/engine/pbr.hlsl");  // Different!
// hash2 != hash1 because includes changed
```

### Shader Cache

Compiled bytecode is cached by content hash:

```
cache/shaders/
├── dx12_sm66/
│   ├── manifest.json
│   ├── a1b2c3d4e5f6g7h8.dxil   # Cache entry
│   └── ...
└── dx12_sm5/
    └── ...
```

**Cache lookup:**
1. Compute xxHash64 of shader (see above)
2. Check if `cache/shaders/{backend}/{hash}.dxil` exists
3. If yes → load bytecode, skip compilation (instant)
4. If no → compile via DXC, store result (first build is slow)

**Cache invalidation:**
- Automatic. When source changes, hash changes, and the old cache entry is never looked up again.
- No explicit `--clear-shader-cache` needed (though cleaning cache/ directory will force recompile).

**Manifest.json** is for debugging only — maps each hash back to the shader path and compilation timestamp. Never used for cache hit/miss decisions.

## Hot-Reload (Development Only)

During development, file changes trigger automatic recompilation:

### File Watch Loop

```
┌────────────────────────┐
│ ReadDirectoryChangesW  │  Watch shaders/ directory
│ (Windows) / inotify    │
│ (Linux)                │
└────────┬───────────────┘
         │ File changed: common.hlsli
         ▼
┌────────────────────────────────────┐
│ ShaderSourceManager::OnFileChanged │
├────────────────────────────────────┤
│ 1. Resolve realPath → virtualPath  │
│ 2. Get dependents from graph:      │
│    - pbr.hlsl includes common.hlsli│
│    - lighting.hlsl includes it too │
│ 3. Mark pbr, lighting dirty        │
│ 4. Rebuild dependency graph        │
│    (includes list may have changed)│
└────────────────────────────────────┘
         │
         ▼ (Mark dirty, don't compile yet)
┌────────────────────────────────────┐
│ Next frame when shader needed:     │
│                                    │
│ GetShaderBytecode(pbr_handle)      │
│   └─ If dirty:                     │
│       ├─ Recompute hash            │
│       ├─ Check cache (reuse?)      │
│       └─ Compile if cache miss     │
└────────────────────────────────────┘
```

### Lazy Recompilation

Shaders are **not** recompiled immediately when files change. Instead:

1. **FileWatcher detects change** → marks affected shaders dirty
2. **Next frame calls GetShaderBytecode()** → checks dirty flag
3. **If dirty:** recomputes hash, checks cache, compiles if needed
4. **Clears dirty flag** and continues

**Why lazy?** During rapid iteration, you might save multiple times in succession (fixing a typo, then tweaking a value). Lazy recompile batches these changes — the shader only compiles once when actually needed.

### Dependency Graph

The shader system tracks include dependencies in both directions:

```
Forward:  pbr.hlsl → [common.hlsli, math.hlsli]
Reverse:  common.hlsli → [pbr.hlsl, lighting.hlsl, particle.hlsl]
```

When `common.hlsli` changes, the reverse graph instantly identifies all dependents and marks them dirty.

**Graph operations:**
- Built on startup (fast — just text-scanning for `#include`)
- Updated incrementally when files change
- Handles diamond dependencies (common.hlsli included by multiple shaders)

## Permutations (Feature Flags)

A single shader can compile to multiple variants via pragma directives:

```hlsl
// pbr.hlsl
#pragma uz_permutation HAS_NORMAL_MAP          // bool → 2 variants
#pragma uz_permutation SHADOW_QUALITY LOW MEDIUM HIGH  // enum → 3 variants
// Total: 2 × 3 = 6 variants per backend
```

Each permutation gets a unique `compile_defines` string, which feeds into the hash:

```cpp
// Variant 1: HAS_NORMAL_MAP=0, SHADOW_QUALITY=LOW
hash = xxHash64(source + includes + "SHADOW_QUALITY=LOW" + "HAS_NORMAL_MAP=0" + ...);

// Variant 2: HAS_NORMAL_MAP=1, SHADOW_QUALITY=MEDIUM
hash = xxHash64(source + includes + "SHADOW_QUALITY=MEDIUM" + "HAS_NORMAL_MAP=1" + ...);
```

**Guards:**
- Max 256 variants per shader (prevents exponential explosion like UE5's tens of thousands)
- Build system emits error if limit exceeded

**Usage in C++:**
```cpp
std::vector<std::string> defines = {
    "HAS_NORMAL_MAP=1",
    "SHADOW_QUALITY=MEDIUM"
};

uint64_t hash = sourceManager.ComputeIdentityHash(
    "/engine/pbr.hlsl",
    defines,
    ShaderTarget::DXIL_SM6_6,
    dxcVersion
);

// Load with this specific permutation
bytecode = cache.Lookup(hash);
```

## Compilation Targets

UzEngine supports a range of shader models to maximize GPU compatibility:

| Output | Compiler | Backend | GPU Compatibility | Use Case |
|--------|----------|---------|-------------------|----------|
| **DXIL** (SM6.6) | DXC | DX12 | NVIDIA RTX, AMD RDNA | Primary (modern hardware) |
| **DXIL** (SM6.0) | DXC | DX12 | NVIDIA Maxwell, AMD Polaris | Older discrete GPU |
| **DXBC** (SM5.0) | **FXC** | **DX12** | **Pre-Turing GPU (RX 580, GTX 1060)** | **Budget / older GPU** |
| **SPIR-V** (1.6) | DXC | Vulkan | Cross-platform | Cross-platform |
| **MSL** (Metal 3) | DXC | Metal | macOS | macOS (via SPIRV-Cross) |

**Both DXC and FXC are loaded dynamically** (not linked at build time), allowing shipping builds to run without compilers present.

### Dual-Compiler System (Milestone 0.2.1)

The engine automatically selects the appropriate compiler:

- **SM >= 6.0** → DXC (fast, modern DXIL)
- **SM 5.0** → FXC (legacy DXBC, older GPU support)

Shader routing is automatic — you don't need to manually choose. However, if you want to test the SM5.0 path on modern hardware:

```bash
UZ_FORCE_SM5=1 ./uzengine --scene game.uzscene
```

## Shipping Build Pipeline

When packaging for release (`uz_build --ship`):

1. **Enumerate** all `.hlsl` files via ShaderVFS
2. **Expand** all permutations (each variant is a separate compile job)
3. **Compile** for target backend(s) in parallel across CPU cores
4. **Verify** 100% cache hit or compile missing shaders
5. **Pack** all bytecode into `shaders.uzpak` (hash-indexed binary archive)
6. **Strip** ShaderVFS, FileWatcher, DXC from shipping binary
7. **Error** if any shader fails to compile — never ship incomplete

The archive is a simple binary blob indexed by content hash:

```
shaders.uzpak
├── Metadata (version, shader count)
├── [hash1 → 256 bytes DXIL]
├── [hash2 → 512 bytes DXIL]
└── ...
```

At runtime, shader loading becomes a single archive lookup:
```cpp
bytecode = shaderArchive.Load(hash);  // O(1) hash table lookup
```

## SM5.0 Shader Authoring (Legacy GPU Support)

If your shader needs to support older GPUs (pre-Turing NVIDIA, pre-RDNA AMD), you must provide **two separate code paths** — one for SM6.6 bindless, one for SM5.0 traditional binding.

### Why Two Paths?

- **SM6.6 (bindless)**: Uses descriptor heaps and unlimited resource binding
- **SM5.0 (Input Assembler)**: No descriptor heaps, must use fixed vertex layouts and register-bound resources

### The #ifdef UZ_BINDLESS Pattern

```hlsl
// vertex_shader.hlsl

#ifdef UZ_BINDLESS
// ═══════════════════════════════════════════════════════════════════════════
// SM6.6 Bindless Path
// ═══════════════════════════════════════════════════════════════════════════

cbuffer PushConstants : register(b0) {
    uint meshDataIndex;
    uint materialIndex;
};

StructuredBuffer<float3> g_VertexPositions : register(t0, space=0);
StructuredBuffer<float3> g_VertexNormals   : register(t1, space=0);
StructuredBuffer<float4> g_Colors          : register(t2, space=0);

[RootSignature("RootFlags(ALLOW_INPUT_ASSEMBLER_INPUT_LAYOUT), DescriptorTable(SRV(t0, space=0, numDescriptors=1000000)), CBV(b0)")]
float4 main(uint vertexID : SV_VertexID) : SV_POSITION {
    float3 pos = g_VertexPositions[meshDataIndex * 65536 + vertexID];
    float3 norm = g_VertexNormals[meshDataIndex * 65536 + vertexID];

    // Bindless: unlimited descriptor access via indexing
    return float4(pos, 1.0);
}

#else
// ═══════════════════════════════════════════════════════════════════════════
// SM5.0 Input Assembler Path
// ═══════════════════════════════════════════════════════════════════════════

cbuffer PerObject : register(b0) {
    float4x4 worldViewProj;
};

// Input Assembler vertex layout:
// POSITION (float2), TEXCOORD0 (float2), COLOR0 (float4)
struct VS_INPUT {
    float2 position : POSITION;
    float2 uv       : TEXCOORD0;
    float4 color    : COLOR0;
};

float4 main(VS_INPUT input) : SV_POSITION {
    float4 worldPos = mul(float4(input.position, 0, 1), worldViewProj);
    return worldPos;
}

#endif
```

### Compilation: Which Path Gets Used?

When compiling:

- **SM6.6 path** (default on modern GPUs):
  - Define `UZ_BINDLESS=1` during compilation
  - DXC compiles the SM6.6 section
  - Bytecode uses descriptor heaps

- **SM5.0 path** (legacy GPU or UZ_FORCE_SM5=1):
  - Define `UZ_BINDLESS=0` during compilation
  - FXC compiles the SM5.0 section
  - Bytecode uses Input Assembler vertex layout

The build system automatically adds the correct define based on target shader model.

### C++ Rendering: Detecting Bindless Support

```cpp
// In your renderer initialization
RHIDeviceDesc desc = /* ... */;
device = CreateRHIDevice(desc);

// Check which path will be used
bool supportsBindless = device->GetShaderModel() >= ShaderModel::SM6_0;

// Pass to rendering systems
textRenderer.Init(supportsBindless);    // TextRenderer adapts internally
statsOverlay.Init(supportsBindless);    // StatsOverlay adapts internally
```

### Input Assembler Vertex Format (SM5.0)

The standard SM5.0 vertex input format used throughout the engine:

```cpp
struct Vertex {
    float x, y;          // POSITION (relative to camera, 2D projected)
    float u, v;          // TEXCOORD0 (texture coordinates)
    float r, g, b, a;    // COLOR0 (vertex color / text rendering tint)
};
```

Set via Input Assembler during render:

```cpp
// C++ (SM5.0 path only)
D3D12_VERTEX_BUFFER_VIEW vbView;
vbView.BufferLocation = vertexBuffer->GetGPUVirtualAddress();
vbView.SizeInBytes = bufferSize;
vbView.StrideInBytes = sizeof(Vertex);
cmdList->IASetVertexBuffers(0, 1, &vbView);

// Then dispatch
cmdList->SetDescriptorTable(0, fontAtlasDescriptor);  // t0 in root signature
cmdList->DrawInstanced(vertexCount, 1, 0, 0);
```

## Post-Switch Compilation

If the user changes `--rhi` or `--shader-model` at startup:

```bash
./uzengine --rhi vulkan --shader-model sm6.0
```

The system:
1. Scans manifest for shaders cached for `(Vulkan, SM6.0)`
2. If all present → proceed normally
3. If any missing → compile before first frame:
   - **Headless:** log progress to console
   - **Windowed:** display loading screen with progress bar
   - **Parallel:** compile across all CPU cores

This mirrors UE5's DDC (Derived Data Cache) model — shaders are compiled lazily per backend and reused across runs.

## Quick Reference

### C++ API

```cpp
#include "core/shader/shader_vfs.h"
#include "core/shader/shader_source_manager.h"
#include "core/shader/shader_cache.h"
#include "core/shader/shader_pipeline.h"     // High-level compile orchestrator
#include "core/shader/shader_reflection.h"   // SPIRV-Reflect binding extraction
#include "core/shader/shader_permutation.h"  // Feature flag variant expansion

// Mount virtual directories
ShaderVFS vfs;
vfs.Mount("/engine", "shaders/engine");
vfs.Mount("/game", "shaders/game");

// Load a shader
ShaderSourceManager sources(vfs);
auto sourceInfo = sources.LoadSource("/engine/pbr.hlsl");
// → includes all parsed, hash computed

// Compute permutation hash
uint64_t hash = sources.ComputeIdentityHash(
    "/engine/pbr.hlsl",
    {"HAS_NORMAL_MAP=1", "SHADOW_QUALITY=MEDIUM"},
    ShaderTarget::DXIL_SM6_6,
    dxcVersion
);

// Check cache
ShaderCache cache("cache/shaders/dx12_sm66");
if (cache.Contains(hash)) {
    bytecode = cache.Lookup(hash);  // Cache hit
} else {
    bytecode = DXCCompile(source, defines);
    cache.Store(hash, bytecode);     // Cache miss, store for next time
}
```

### File Watching (Dev Only)

```cpp
#include "core/shader/shader_hot_reload.h"

FileWatcher watcher("shaders/");
watcher.OnChange([&](const Path& realPath) {
    // File changed: resolve which shaders are affected
    auto virtualPath = vfs.FindVirtualPath(realPath);
    auto dependents = graph.GetDependents(virtualPath);

    // Mark all dependents dirty (recompile on next use)
    for (const auto& dep : dependents) {
        MarkShaderDirty(dep);
    }
});
```

## Troubleshooting

### Shader Compiles Slowly After Code Change
**Cause:** First use after file change compiles on the game thread, causing a frame hitch.

**Solution:** Adjust update loop to preemptively compile dirty shaders:
```cpp
// In update loop, before rendering
for (const auto& [name, shader] : shaders) {
    if (shader->isDirty) {
        shader->EnsureCompiled();  // Compile on update thread
    }
}
// Render thread: all shaders ready to use
```

### Cache Bloat (Hundreds of Old Entries)
**Cause:** During development, permutation experiments accumulate old unused cache entries.

**Solution:** Periodically prune cache:
```bash
# Delete entire cache (will recompile from scratch)
rm -rf cache/shaders/

# Or: let the build system GC after shipping build
uz_build --ship  # Cleans unused entries during packaging
```

### Hash Mismatch Between Machines
**Cause:** DXC version differs, or include path resolution differs.

**Solution:** Ensure all machines use same DXC version:
```cpp
// Verify DXC version before caching
auto dxcVersion = compiler.GetVersion();
if (dxcVersion != expectedVersion) {
    UZ_LOG_WARN("DXC version mismatch: expected {}, got {}",
                expectedVersion, dxcVersion);
    // Clear cache for this machine to recompile
}
```
