# Flicker elimination — hypothesis ledger

Programme: `.rulebook/tasks/phase0_sponza-followup-09..14`. This file is the single place where a
hypothesis about the Sponza flicker is recorded, decided or left open. It is appended to, never
rewritten: a verdict that later turns out to be wrong gets a new row that supersedes the old one,
with both visible.

Every row carries: ID, ROI, prediction, intervention, controlled settings, the pipeline actually
active, the stage and unit measured, the reference used, the number of valid samples, the
repeatability of the metric, the observed result and the verdict.

Verdicts are only one of:

* **supported (in scope)** — the prediction held under the tested conditions, which are named.
* **rejected (in scope)** — the prediction failed under the tested conditions, which are named.
* **inconclusive** — the experiment ran but the effect is below the measurement sensitivity, or a
  confound was not controlled. A null result below sensitivity is inconclusive, never "no effect".
* **open** — not yet tested; the next discriminating experiment is named.

A diagnostic task may finish with inconclusive rows, provided its experiments were actually run and
the next discriminating test is written down. That does not close the visual defect.

## Measurement protocol (followup-09)

| Item | Value |
|---|---|
| Primary metric | `std_mean`: mean over ROI pixels of the temporal standard deviation of the TAA output's linear Rec.709 luminance (scene radiance units) |
| Secondary metrics | `abs_diff_mean` (mean absolute frame-to-frame change), `std_p99` (bright-side tail), ROI mean (energy drift) |
| Tertiary metrics | display-referred counts on 8-bit sRGB PNGs (`count_gt_40` code values). Never sufficient on their own: exposure and bloom change the count without changing the radiance |
| Capture | `uzengine.exe --region-dump` v2 records, full resolution, no subsampling; GPU frame stamps checked on every file |
| Sequence | 200 warm-up frames, then 256 measured frames, camera still, one continuous process per run |
| Runs | 3 independent runs per pose |
| Poses | W (`scripts/sponza-flicker-w.uzproject`), A (`scripts/sponza-flicker-a.uzproject`) |
| ROIs | W: `window`, `shadow_wall`. A: `rear_door`, `right_shadow`, `lit_floor` |
| Jitter | `r.TAA.JitterSequenceLength=8` (production default). Length 1 is a constant Halton23(1) = (0, −0.167) px offset, a control, not zero jitter |
| Exposure | Fixed (`r.AutoExposure=0`) for every comparison of display-referred quantities. Auto-exposure adapts with `dt`, so any change in frame cost moves the displayed image (measured: 1 code value between an instrumented and an uninstrumented run at identical settings) |

### Predeclared decision rule

Fixed before any candidate is evaluated (followup-09 item 1.6), from the baseline repeatability in
`.screenshots/flicker-elimination/09-validate-flicker-capture/baselines.json` and the synthetic
accuracy bounds in `scripts/test_flicker_metrics.py`:

1. A difference in the primary metric counts only if it exceeds
   **max(3 × the 95 % half-width of the baseline repeatability for that ROI, 5 % of the baseline
   mean)**. Anything smaller is reported as inconclusive.
2. The evaluation pixel set of an ROI is frozen from the baseline (`valid in every frame`) before
   candidates are compared. Re-selecting each candidate's worst pixels is not allowed.
   Per-ROI thresholds measured on 2026-09-09 (linear radiance): W `window` 4.8e-4,
   W `shadow_wall` 4.7e-7, A `rear_door` 8.9e-6, A `right_shadow` 2.1e-5, A `lit_floor` 5.0e-5.
   Run-to-run reproducibility is far tighter (95 % half-widths 1e-10 to 8e-8) because the renderer
   is deterministic at a given frame index, so the 5 %-of-mean rule is what actually binds.
3. Measurement accuracy is bounded by the synthetic checks: amplitude recovery within 2 %, exact
   period recovery, exact counts. A claimed effect smaller than those bounds is inconclusive.
4. No hypothesis is rejected on a display-referred threshold count alone; the linear metric decides,
   and the display number is reported next to it.
5. A candidate that improves the metric by removing signal — blur, lower exposure, missing lighting
   or retained invalid history — fails, whatever the metric says (followup-14 item 1.5).

### Review of this evaluation (2026-09-09), and what it changed

The task was reported as complete. An independent re-inspection of the code, the report, the
aggregates and the tests found six defects. The decision not to adopt the candidate survives all of
them, but the evaluation could not be treated as closed, and the task was reopened.

1. **H-24's premise was false.** It proposed a "reversible-tonemap reconstruction" as an unbiased
   next mechanism. Averaging in `c/(1+Y)` and inverting is *exactly* a weighted mean with weights
   `1/(1+Y)` — the same family as the shader's `1/(4 + exposure*Y)`, with a smaller constant, so it
   is *more* aggressive, not unbiased. On two samples 0 and 8 it returns 0.8 where the linear mean
   is 4. Verified to 2.4e-13 over 20 000 random cases. H-24 is now recorded as rejected on paper,
   H-24b states what the exponent sweep already proves about the whole family, and H-25 names a
   mechanism that is actually different.
2. **A gate could pass on missing evidence.** The evaluator tested `paths_equal is not False`, so a
   `None` — no lighting-path capture for that variant — passed. The report printed
   "lighting paths identical: None" for exponent 0.5 while G7 was scored as if verified. Gates are
   now tri-state and missing evidence reads **inconclusive**, which is not a pass. The missing
   capture was then taken.
3. **The reference was not what the claims needed.** Everything was measured against the
   cycle-averaged raw input, an 8-sample estimate built from the same jitter offsets under
   examination, and "the gain is not blur" rested on the output moving towards the *instantaneous*
   sample, which carries jitter-dependent coverage of its own. An independent converged spatial
   reference (`r.TAA=0`, `r.ScreenPercentage=200`, box-downsampled) was built, and sharpness is now
   measured on real scene content by gradient energy rather than inferred.
4. **Two required conditions were not tested.** Item 1.4 asks for exposure transitions and clipmap
   crossings; both were held fixed, on the grounds that followup-11 and followup-13 own those
   systems. Those tasks characterised the systems, not their interaction with this candidate.
   Measured in `coverage.json`. Separately, G5 was written as *GPU* frame time and only CPU wall
   time was ever recorded; the run manifest now carries per-pass GPU timings, which the render
   graph had been collecting all along.
5. **G6 read one repeat of three.** It now takes the worst case across every repeat and reports the
   spread. (The three repeats turn out to be identical, but the verdict no longer depends on that.)
6. **The recorded status contradicted the checklist.** `.metadata.json` still said `pending` while
   every item was ticked.

A seventh, found while fixing the others: the run manifest reported the *window* size as the render
resolution, so a 50 % capture claimed 1920x1080 while the log showed the renderer had resized to
960x540. The measurements were unaffected — the TAA output is at output resolution either way — but
the provenance record was wrong, and it is the record used to prove two runs were configured the
same. Fixed in `runtime/tools/uzengine.cpp`.

### Two findings about the measurement itself (followup-14)

**The primary metric answers a different question than the one asked.** `std_mean` is the temporal
standard deviation of the output: it measures *stability*, not *correctness*. A bright feature
reconstructed at its correct energy carries more absolute variance than the same feature crushed to
a fraction of it, so a change that fixes the reconstruction can raise the metric. Measured against
the cycle-averaged raw input - the correctly resampled image - the candidate is more accurate on
every ROI tested:

| ROI | error vs reference, baseline -> exponent 0 | bright-side energy (1.0 = correct) |
|---|---|---|
| W `window` | 0.2199 -> 0.0726 | 0.9715 -> 0.9947 |
| A `rear_door` | 0.0157 -> 0.0080 | 0.4202 -> 0.7446 |
| C `small_window` | 0.2522 -> 0.0812 | 0.9509 -> 0.9909 |

Pose A `rear_door` is the clearest case: the baseline holds only
42 % of the correct bright energy
there, the candidate raises it to
74 % and halves the
per-pixel error, while `std_mean` **doubles**. Read against the baseline alone that looks like a
severe regression, and it was recorded as one until the reference was measured. G1 was frozen and
it fails, and it is reported as failing - but a future gate for this defect must be stated against
a reference, not against the previous frame. The residual is a symptom; the reconstruction error is
the defect.

**The renderer is not bit-reproducible across processes.** Four captures of an identical
configuration (`scripts/diagnose_cvar_ulp.py`, 8 frames x 98 304 px x 3 channels) differ in up to
795 of 786 432 recorded values, by up to 1.6e-2 in linear radiance; every configuration tested
shows it, and which values move varies between runs. Consequences, all of them recorded rather than
worked around:

* aggregate statistics are unaffected - the three repeats of every gate agree to ~1e-13, against
  effects of 1e-3 - so the conclusions above stand;
* any assertion of *bit*-identity is invalid. Two behavioural checks that assumed it failed
  spuriously and were rewritten to compare against a measured per-configuration floor;
* comparisons must therefore be made on aggregates over a run, never on single frames or pixels.

**Corrected 2026-09-15.** "The three repeats of every gate agree to ~1e-13" does not hold for every
configuration. On pose A `rear_door`, 128 frames with the `components` fields, three processes of one
binary (fnv1a64:83d15259f19c92f4) and one configuration differ by up to 2.31e-06 relative in mean
energy and 2.43e-04 in oscillation, with up to 19 % of pixel-frames differing; two of the three agree
to about 1e-08 and the third departs from both (`34-c0-process-floor`, followup-12 notes). In
absolute terms the oscillation spread is 4.3e-08, two orders under that region's followup-09 floor of
8.9e-06, so decisions made against that floor are unaffected. A tolerance set tighter than a measured
same-configuration floor is not.

This is a confound for the whole programme, not only for this task, and it was not known when
followup-09 declared the renderer deterministic ("run-to-run delta 0"). That statement holds for
the aggregate metrics it was measured on, and only for those.

### A reader bug, and what it cost (2026-09-10)

`scripts/flicker/regiondump.py` stores each field group's record count twice, in `field_offsets()`
and in `records_per_pixel()`. Adding a record to TAA_EXTRA updated only the second, so every
LIGHTING_EXTRA channel was read one record early for a day. It produced one retracted ledger row
(H-29) and invalidated the controls of another (H-28), and it was found only by dumping all 16
record slots for a single pixel and matching them against the shader's write order.

Two consequences beyond the retraction:

* `field_offsets()` now asserts that its running total equals `records_per_pixel()`, so the two
  cannot diverge silently again;
* **the archived dumps from before the change can no longer be read at all** — they carry 15
  records per pixel and the current reader expects 16, and the integrity check rejects them. The
  region dump has no format version for the *group sizes*, only for the header, so an instrumentation
  change retroactively invalidates every stored capture. Preserving dumps is not sufficient for
  auditability on its own; the format they were written with has to be preserved with them.

### What the isolation matrix settled, and what it did not (2026-09-10)

The matrix answered the question the sized-ratios could not. With AO and specular held at the
reference's own per-frame, per-pixel values while the gather is frozen, the reduction survives
whole: the isolated drop is 100.1 % of the original in all three repeats. The interference was
along for the ride, not carrying the effect.

Three things remain open, and none of them blocks the wall investigation:

* **The AO/specular divergence is still unexplained** and is now tracked as a candidate defect in
  its own right rather than as a confound of this result. What is known: specular diverges on the
  same frame the frozen texture is first reused, AO diverges in a nine-frame transient, the SSGI
  pass's second output is not consumed by the lighting shader, and feedback through the previous
  frame's TAA history is excluded. A shared resource or a synchronisation gap are not.
* **Freezing the output is a diagnostic, not a correction.** It demonstrates where the residual
  comes from; it cannot ship, because a frozen gather stops responding to anything.
* **Which stage inside the gather varies is unknown.** Sampling, spatial reconstruction, the
  gather's own reprojected history and its history weighting are all candidates, and the next step
  observes all of them in one sequence before intervening in any.

### Pre-registered criterion for the isolated H-28 re-evaluation (2026-09-10, before capturing)

Two limits on what step 1 established, kept explicit because both were nearly overstated:

* bit-identity up to frame 301 excludes divergence *earlier in that capture*. It does not exclude
  aliasing or synchronisation that only changes once the pass stops executing — which is precisely
  the condition under test;
* specular diverging at 302 rather than 303 contradicts feedback through the previous frame's TAA
  history. It does not identify a legitimate same-frame dependency: a shared resource or a missing
  barrier remain open, and neither has been tested.

**The matrix.** Four conditions, three repeats each, same ROI, same window, same metric:

| condition | gather | AO and specular |
|---|---|---|
| reference | normal | normal |
| substitution control | normal | replayed from the baseline |
| original intervention | frozen | normal |
| isolated intervention | frozen | replayed from the baseline |

**The replay is per frame and per pixel**, taken from the baseline run's own recorded values at the
matching frame index — not one frozen frame held constant, which would introduce a second temporal
change and confound exactly what is being separated.

**Thresholds, fixed now.**

1. *Substitution control.* Row 2 must reproduce row 1: oscillation within **5 %** and mean energy
   within **0.5 %**. If it does not, the replay mechanism alters the result by itself and no row
   below it can be interpreted.
2. *Isolated intervention.* At least **80 %** of the original reduction must survive. The original
   is 8.621e-06 -> 1.564e-06, a drop of 7.06e-06, so row 4 must fall by at least **5.65e-06** from
   row 1, in every repeat.
3. *Energy.* Row 4's mean radiance must stay within **1 %** of row 1's.
4. *Per frame, not only in the mean.* The frame-by-frame difference is reported for every row, so a
   transient like the AO burst at frames 349-357 cannot be averaged out of view.

**What the outcome licenses.** If the reduction survives, H-28 gains causal support *within the
static wall's scope*, even with the origin of the AO/specular interference still open — that
interference then remains a separate candidate defect to be explained, not something the result
depends on. If the reduction does not survive, the earlier -81.9 % was carried by the interference
and H-28 is rejected. Either way, the previous evaluation is kept: this is an additional row, not a
rewrite, and H-28 is not promoted retroactively.

### Where the AO and specular changes come from (step 1 of the H-28 re-evaluation)

The isolation breach was traced rather than assumed, from the archived midway capture where the
freeze lands mid-window and everything before it must be identical.

* **Nothing differs before the freeze frame.** Consumed texture, AO and specular are bit-identical
  between baseline and frozen up to frame 301, which rules out pre-existing nondeterminism and any
  render-graph aliasing that would differ from the first frame.
* **Specular diverges at frame 302** — the same frame the frozen texture is first reused, not the
  one after. A same-frame dependency, so not feedback through the TAA history. Mean difference
  3.76e-08 on a signal whose own temporal variation is 1.14e-05.
* **AO diverges only on frames 349-357**, nine consecutive frames out of 128, by 5.07e-05 on a 0..1
  quantity, and is bit-identical on the other 119. A transient, not a persistent offset.
* **The SSGI pass does have a second output** — `SSGIRenderer::GetAOResultSrvIndex` — and the
  per-frame CB carries it as `ssgiAOSrvIndex`. But `deferred_lighting_ps.hlsl` declares `_ssgiAO`
  and never reads it, so the AO the lighting pass uses is the G-buffer mesh AO times GTAO. The AO
  change is therefore *not* that second output, which is what the inspection was for: the guess
  that the pass simply delivers more than one consumed result is wrong.

The specular route is not yet identified — a same-frame dependency is consistent with the radiance
cache or a shared trace being updated from the gather within the frame, but that is a hypothesis and
has not been tested. The AO transient's cause is unknown.

### The isolation criterion, and what it actually detected (2026-09-10)

H-28b's controls were fixed before capturing, and two of the three passed outright: the consumed
gather texture stops updating on exactly the predicted frame, and the SDF mode is active throughout.
The third — "direct light, reflections, AO, exposure and geometry stay within the measured
repeatability floor" — failed, on specular (3.9e-08 against a floor of 1.3e-11) and AO (3.6e-06
against a floor of exactly 0.0).

The rule voids the run, and it has been applied. The breach was *sized* rather than argued away:
specular 2.4e-09, AO bounded at 3.7e-12, diffuse indirect 1.08e-05, against an oscillation drop of
7.06e-06. Those are ratios between standard deviations and mean differences, **not additive causal
shares** — the diffuse figure exceeding the drop is itself the proof they cannot be read that way,
since a TAA-filtered chain does not decompose linearly. They bound orders of magnitude; they do not
establish that the breach is harmless.

A zero floor does not mean the control misfired. It detected a **reproducible change outside the
intended component**, which is exactly its job, and step 1 above confirms the change is real and
lands on an identifiable frame. What is wrong is the *demand*: absolute identity, when the question
is whether that change compromises the attribution. A criterion of practical relevance has to state
a margin and measure the external components' influence on **the same final metric** H-28 is
claimed on — not compare standard deviations across different stages and units.

That change is **not** being made unilaterally. The criterion was agreed before capturing, the run
is reported void under it, and the numbers needed to decide whether to refine it are on the table.

### Audit of the layout bug (2026-09-10)

The window is bounded. `field_offsets()` disagreed with the engine only between the commit that
grew TAA_EXTRA from 3 to 4 records and the fix; before it, both sides carried (2, 5, 1, 3, 4) and
agreed. Anything captured *and* read before that is unaffected — including followup-12's original
per-component study, which is why its "97.5 % diffuse indirect" needed no retraction and H-29 did.

What the shift did and did not touch:

* **LIGHTING_EXTRA channels are wrong** in anything read during the window: `direct_light`,
  `diffuse_indirect`, `specular_indirect`, `emissive_and_mis` (the path bitmask) and the
  metallic/AO/shadow components carried in their fourth slots. Each was read one record early.
* **LIGHTING and TAA channels are unaffected.** Their offsets are 0 and 2, computed before the
  group whose size changed, so they never moved. `taa_output`, `taa_raw`, `taa_filtered`,
  `taa_history`, `taa_clamped` all read the records they always did.
* **TAA_EXTRA channels are unaffected.** Its *base* is the sum of the groups before it, none of
  which changed; only its own size was wrong, which shifts what follows it, not itself. So the
  clamp box, the plus taps and the history sample position were read correctly.
* **The pixel stride is unaffected.** It comes from the header's `recordsPerPixel`, which the
  engine computed with the correct counts throughout. `scripts/test_region_format.py` now checks
  stride and slot mapping against a fixture with a distinct value per pixel and per record.

### Review of H-25 / H-26 / H-27 (2026-09-10), and what the verdicts actually support

An independent review found five limitations. All five hold, and the rows above are qualified here
rather than rewritten, in keeping with this file's rule.

1. **H-27's accumulator is not the one in the shader.** The model uses a constant coefficient, the
   median `blendFinal` of 0.04. The shader passes that through `WeightedLerpFactors` together with
   HDR weights computed from the *current* filtered and clamped luminance, so the effective
   coefficient is state-dependent. Measured on the recorded records: the effective filtered fraction
   has median 0.0400 but a p05-p95 range of 0.0390-0.3000. The constant-coefficient
   IIR is therefore an approximation, and H-27 stands as an **approximate amplitude model**, not as
   a description of the operator.
2. **The prediction applies the fundamental's gain to the total variance.** A jitter-periodic input
   has harmonics; multiplying its whole standard deviation by `|H(2*pi/N)|` is not the filter's full
   response even for a linear IIR. The agreement (1.20 / 1.21 / 0.79) is amplitude agreement, and
   phase, harmonics and per-pixel time series were not reproduced.
3. **H-25's "11 %" is a one-step sensitivity, not a steady-state contribution.** The one-step
   counterfactual swaps the bounds but reuses the recorded history, so it measures how much the
   change moves a single frame. How that change propagates through the accumulation was not
   measured. The correct statement is "a small immediate effect under this control", and the
   steady-state share of the clamp remains unmeasured.
4. **H-26's rejection was too strong.** It compared an instantaneous perturbation
   (2.6e-05 mean, at the time reported as 2.3e-4 on the
   output) against a temporal standard deviation — different statistics — and no intervention ever
   replaced the history read with an exact one *during a run*. A small perturbation applied every
   frame can accumulate. H-26 is downgraded to **not demonstrated as a dominant cause, and not
   eliminated in steady state**.
5. **H-27's negative control does not gate its verdict.** The no-jitter condition is recorded but
   the automatic verdict rests only on the three ratios and their ordering. In that control the
   median `blendFinal` moves from 0.04 to 0.30 (the anti-flicker guard), so it is not the same
   accumulator with a constant input, and it cannot be read as one.

**Auditability.** The three screening scripts deleted their raw dumps after aggregating, so phase,
harmonics and alternative interventions could not be recomputed without recapturing. The full
recurrence replay now keeps its dump under
`.screenshots/flicker-elimination/15-isolate-clamp-bounds/raw/full-recurrence/`, and
`scripts/analyze_recurrence_error.py` reads it without touching the GPU.

### State of the full-recurrence replay (2026-09-10, after the three-step isolation)

The replay was asked to reproduce the shader's whole loop before attributing anything to a
mechanism. It does not, and the reason is now isolated rather than guessed at. The history sample
position the shader uses is recorded in the region dump (TAA_EXTRA gained a fourth record), so the
three candidate explanations could be separated in order, each gating the next:

| step | question | result |
|---|---|---|
| 1. coordinates | does the replay reconstruct the sample position the shader used? | **yes** — \|dx\| mean 5.08e-05, max 1.22e-04 px; \|dy\| mean 1.07e-05, max 3.05e-05 px |
| 2. isolated read | at the *recorded* position, does the Catmull-Rom reproduce the recorded history? | within the 1e-3 gate (max 8.14e-04) but with a structured tail: mean 2.58e-05, above 1e-4 on 6.5 % of samples |
| 3. chained | does the 64-frame recurrence hold? | **no** — max 7.17e-03, crossing 1e-3 at frame 2 |

What this settles, and what it does not. The velocity dilation was a *hypothesis of mine and it
was wrong*: the recorded `velocityPixels` is already loaded at the dilated coordinate. But
"coordinates exonerated" was too strong, and measuring the displacement's effect rather than its
size shows why: the residual displacement is 5.45e-05 px on average, and
`|grad(history)| x |dpos|` accounts for **26 % of the
observed read error** overall and 21 % on the top 1 %
gradient pixels (2.96e-04 against an observed
1.44e-03). So position is a *minority contributor that has not been
eliminated*, not an exonerated one, and the remaining three quarters are filtering or precision.

The chained growth was described as a random walk because it resembled sqrt(n). That was a
resemblance between maxima, not evidence, and the signed statistics reject it: the per-frame error
has a signed mean of 1.37e-04 against an absolute mean of 1.37e-04 —
it is **one-sided, essentially pure bias** — and its centred part is autocorrelated at
lag 8 (+0.53) while being near zero at lags 1, 2 and 4
(-0.08, -0.07, -0.08). Lag 8 is the jitter cycle, so the
error is phase-locked to the jitter rather than independent between frames. A bias integrates
through an accumulator roughly linearly and saturates at about `1/alpha` times its per-frame size;
that, not a random walk, is what the growth curve shows.

Accordingly the replay is **adequate to the chosen threshold for an isolated read and inadequate
for the recurrence**, which is a narrower statement than "faithful for one frame": the 6.5 % tail
is present in the isolated read too. Nor do these data show that reproducing the filtering offline
is intractable — the error is structured and one-signed, which is the opposite of hopeless. What
they show is that chasing it stopped being the shortest path to the question actually being asked.

**Consequence: the offline replay cannot validate a correction, and the GPU is the shorter path.**
The replay keeps its use as a one-step screen, which is what H-25 relied on and all it supports.
Any steady-state attribution — the clamp's real share, whether the history read accumulates,
whether a stabilised bound helps — is to be done by putting the intervention behind a CVar in the
shader and measuring on the GPU with the followup-14 protocol. That is a decision about priority,
not a proof that the offline route is closed.

The flicker on the shadowed walls and in motion remains outside all of this.

## Confounds recorded so far

* **Comparing the same screen pixel is not a lighting measurement while the camera moves.** On this
  trajectory the same-pixel difference is 4.3x the motion-compensated one (7.8e-4 vs 1.8e-4), and the
  first version of the tracking (a single mid-depth unprojection under a reversed-Z projection) was
  off by 21 px and would have reported no effect at events at all.
* **The deferred lighting records do not cover the forward translucent pass.** Two of the three
  reported regions get essentially all their colour from it, so their composition check fails by
  construction and no GI control moves them. Check the pass before attributing a region.
* **A freeze must be applied after convergence.** Freezing the radiance cache from frame 0 held a
  state that had never converged (the first version of the control also disabled the whole SDF GI
  path, which the recorded path bits caught); `r.GI.RadianceCache.FreezeAfterFrame` freezes at a
  chosen frame and keeps the path active.
* **`r.GI.Reflections=0` substitutes rather than subtracts.** The specular radiance starts as the
  prefiltered IBL cubemap and is overwritten by the SDF trace only when reflections are on, so the
  control replaces an occluded term with an unoccluded one: the interior gets 11x brighter and the
  auto-exposure operating point drops 16x.
* **`r.TAA.PreExposeWeights` is a no-op at a fixed exposure of 1.0**, because it multiplies the
  resolve's HDR weights by the frame exposure. Any evaluation of it must run at the exposure the
  scene actually uses, with a control at the same exposure.
* **Bloom's effect on a threshold count changes sign with the exposure**, so a count difference
  between two runs is only interpretable when the exposure is fixed and stated.
* **Per-mask energy ratios are redistribution, not loss.** A reconstruction filter moves light
  across a mask boundary, so the dark bars read 69x (production) to 381x (no HDR weighting) the
  radiance their own raw samples have. Only a whole-ROI energy ratio is an energy statement.
* **An `r.TAA=0` run cannot be measured with the resolve's own records** — the pass never runs, so
  the records are stale and the file is flagged. The no-TAA image is measured instead from the
  `taa_raw` record of a TAA-on run, which is the same jittered sample without accumulation.
* **Per-mask energy ratios are redistribution, not loss.** A reconstruction filter moves light
  across a mask boundary, so the dark bars read 69x (production) to 381x (no HDR weighting) the
  radiance their raw samples have. Only a whole-ROI energy ratio is an energy statement.
* **A `r.TAA=0` run cannot be measured with the resolve's own records** — the pass never runs, so the
  records are stale and the file is flagged. The no-TAA image is measured instead from the `taa_raw`
  record of a TAA-on run, which is the same jittered sample without accumulation.
* **Auto-exposure is frame-time dependent** (`auto_exposure.cpp` uses `dt`): any change in cost —
  including switching the diagnostics on — moves the displayed image. Measured as 1 code value
  between instrumented and uninstrumented runs of identical settings; identical (0) once the
  exposure is fixed. Every display-referred comparison must fix the exposure.
* **Display counts are not energy**: a threshold count changes with exposure and bloom while the
  radiance is unchanged (H-02, H-05).
* **Fixed-screen ROIs in motion** contain different surfaces from frame to frame; a mean change is
  not a lighting discontinuity (H-07).
* **PNG frame indices before 2026-09-09** were one render frame ahead of their file name
  (`--screenshot-frames` requested the capture after `RenderFrame(N)`), so display and record
  frames from older packages must be aligned by +1.
