GODOT'S RENDERING APPROACH (FORWARD CLUSTERING)
================================================================================

Pipeline:
  1. Cull geometry → opaque, transparent, secondary lists
  2. Render shadows (directional CSM, omni/spot atlas)
  3. GPU compute: build light clusters per screen tile
  4. Single forward pass: for each pixel, fetch lights from cluster, apply BRDF
  5. Post-process: tonemap, bloom, SSAO, SSR, TAA

NOT Deferred:
  - No GBuffer passes
  - No per-light lighting passes
  - Transparency blends naturally
  - MSAA works without extra complexity

Clustering:
  - Screen divided into 16x16 tiles
  - GPU compute assigns lights to tiles
  - Shader reads cluster buffer, applies all affecting lights
  - Scales linearly with light count (no O(n²))

8 ARCHITECTURAL DECISIONS GODOT MADE
================================================================================

1. FORWARD CLUSTERING
   Why: Simpler, better transparency, less memory bandwidth
   Result: Single forward pass instead of N+2 deferred passes

2. UNIFIED LIGHT DATA
   Why: Zero divergence, GPU cache coherent, scalable
   Result: One struct for all light types, no if-branching in shader

3. ENVIRONMENT BLOB
   Why: Single versioning, cache locality, easier hot-reload
   Result: All ambient/fog/tonemap in one resource

4. SHADOW ATLAS + REALLOC
   Why: Memory efficient, no allocation failures
   Result: 32+ lights can shadow from one 2K texture

5. SHADER VARIANT CACHE
   Why: Compile only used paths, reduce dead code
   Result: Cleaner shaders, fewer registers used

6. RENDERINGDEVICE ABSTRACTION
   Why: Portable, thread-safe, vendor-agnostic
   Result: Easy to swap Vulkan/DX12/Metal backends

7. EXPLICIT DEFAULTS
   Why: Predictable behavior, no null checks
   Result: New project renders correctly immediately

8. COMPUTE SHADERS FOR BUILD
   Why: CPU-free, highly parallel, scales to thousands
   Result: Light clustering, IBL baking, visibility culling all on GPU

CODE QUALITY LESSONS
================================================================================

Godot's Rendering Code Is Lean Because:

1. Single responsibility per file
   - light_storage.h: lights only
   - shadow_atlas.h: shadow atlas only
   - cluster_builder.h: clustering only
   - No 2000-line monoliths

2. Data-driven not switch-on-type
   - LightData struct with type enum
   - No if (light.type == ...) { ... } else { ... }
   - Shader: loop over light array, apply unified BRDF

3. Abstraction boundaries are enforced
   - RenderingDevice hides DX12/Vulkan/Metal
   - No ID3D12Device* in game code
   - Portable from day one

4. Explicit over implicit
   - Every resource has defaults
   - No "uninitialized" state
   - Constructor initializes all members

5. GPU-centric thinking
   - Offload CPU work: light culling, IBL baking, visibility
   - Minimize game thread CPU cost
   - Compute shaders for SIMD-friendly algorithms

================================================================================
KEY TAKEAWAY
================================================================================

Godot's renderer is lean (50K LOC vs 200K+ in UE5) because it:

1. Chose a simpler base (forward clustering vs deferred)
2. Unified data structures (one light struct, not N variants)
3. Offloaded to GPU (compute shaders, no CPU culling)
4. Avoided premature optimization (generic abstraction, not special cases)
5. Enforced boundaries (RHI abstraction from day one)

UzEngine can achieve similar leanness by adopting these patterns incrementally.
The cost of refactoring now is paid back within 2 sprints via:
  - Simpler maintenance
  - Faster shader compilation
  - Easier debugging
  - Better scale to 100+ lights
  - Cleaner codebase for new engineers
