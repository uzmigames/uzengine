## Initial implementation

- `cloud_raymarch_cs.hlsl:237`: `EvaluateMultiScattering` evaluates the
  reference's eight bounded orders, including direct scattering, with
  scattering/extinction/eccentricity factors a=b=c=0.5. `LightMarch`
  returns optical depth rather than prematurely exponentiating it, so
  higher orders still receive light in optically thick regions.
- `cloud_raymarch_cs.hlsl:534-543`: the constant ambient approximation and
  unconditional Beer-powder blend are replaced with the octave source plus
  `SH_L0 * (1 / (4 * PI)) * heightFraction * skyLightScale`.
  The existing serialized `ambient_multiplier` is retained as
  `skyLightScale`; it no longer supplies constant ambient energy.
- Powder is optional, default off: `1 - powderScale *
  exp(-extinction * powderExponent)`, with defaults 0 and 2.
- `ACCURATE_PHASE_FUNCTION=1` enables the optional normalized HG/Draine
  mixture (0.988, 0.556, 22, 0.482). The default remains component-controlled
  dual HG. Higher orders attenuate both eccentricity and Draine's alpha
  toward isotropic scattering.
- Component JSON keys are `powder_scale`, `powder_exponent`, and
  `multi_scatter_octaves`; defaults are 0, 2, and 8. Component values reach
  CloudPass through three added assignments in the already-dirty
  `frame_atmosphere_passes.cpp`.
- New CB offsets are 312, 316, and 320. The allocation is still 512 bytes,
  root constants still 12 DWORDs, and the global root signature is untouched.
  The 256-iteration primary march and eight-light-step cap are unchanged.
  No temporal filter, runtime noise baking, or density/phase-default retuning
  was introduced.

## Focused regression diagnosis

The owner correctly rejected the first result as a brightness regression.
`runtime/engine/renderer/ibl/sh_projection.cpp:194-225` proves that the
packed sky polynomial reconstructs **E/pi**, not irradiance or the
solid-angle-integrated source assumed by the initial cloud expression.
The passed `.w` is also a compact polynomial constant containing a Y20
term, so calling it a full sky-irradiance lookup overstates its accuracy.

At the reference sun-center pixel, a CPU replay using the shipped R8
volumes, filtered mip chains, captured camera matrix, logged SH values,
STBN frame 181 and the inspected shader's march equations selects this
interior sample:

- Half-resolution pixel (480,270); position
  (17.701716, 0.020250, 6368.237103) km.
- Height fraction 0.210284; density 0.177344; sun optical depth 0.499545;
  view/sun cosine 0.965656.
- M1 incident in-scatter source RGB:
  (5.822177, 5.825777, 5.839577), including sky
  (4.4376, 4.4412, 4.4550).
- Initial M2 source RGB: (1.630209, 1.630269, 1.630500), including sky
  (0.074258, 0.074319, 0.074549).
- M2 sun-octave contributions are additive:
  0.859176 + 0.338609 + 0.175161 + 0.092348 + 0.047801 +
  0.024365 + 0.012306 + 0.006185 = 1.555950, versus M1 sun 1.384577.
  The direct/base term was not accidentally attenuated by later orders.
- The sky source, however, retained only `h/(4*pi) = 0.016734` of M1's
  fill. That unit/normalization error and removal of the base illumination
  explain the darkening; the octave sum itself increased the sun source.

Evidence: `.screenshots/cloud-m2/{replay.py,inscatter-replay.json}`.
This is an instrumented **CPU diagnostic replay**, not a claimed GPU
readback of hidden raymarch variables; the earlier HDR image measurements
are actual GPU output.

The focused correction converts the compact sky radiance proxy to a
`4*pi` integrated isotropic source before phase normalization, and uses
sky visibility `lerp(0.8,1,h)` with scale `ambientMultiplier/0.8`.
This preserves the M1 base illumination while retaining a varying height
gradient, rather than replacing the lost floor with a global arbitrary
brightness multiplier. At the same replayed sample the predicted source
is (6.226840, 6.230629, 6.245154).

The phase sign is correct: `dot(viewRay,towardSun)` is positive looking
at the sun and both lobe eccentricities are applied inside every order.
With the unchanged reference values g1=0.5, g2=-0.3, blend=0.7, the
normalized phase is 0.166312 at cosine +1 and 0.153092 at -1.
The forward peak exists but is weak because the reference deliberately
weights the back-scattering lobe by 70%. The optional HG/Draine path
compiles but is not used to claim a runtime silver lining.

The focused effort stops after this one correction attempt. Keep the
committed M1 renderer, not the darker initial M2 or the brighter but still
unqualified correction. A correct follow-up needs:

1. A unit-consistent, height- and optical-depth-dependent sky transport
   term, rather than calibrating against the legacy fill floor.
2. A verified forward-scattering model/lobe balance, tested on an actual
   cloud silhouette near the sun; the current 70% back-lobe reference and
   fully overcast sun window cannot establish that visual gate.
3. Raw cloud opacity/front-depth and GPU source-term probes so density
   coverage, sky background and scattering can be measured independently.
   The CPU replay here explains the energy loss but is not that GPU probe.
4. The brightness, contrast, silver-lining, temporal and banding gates
   passing together before the M2 change is accepted.
