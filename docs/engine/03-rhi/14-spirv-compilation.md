# RHI — SPIR-V Compilation Pipeline

> **Status**: Done (Milestone 1.3)
> **Source**: `runtime/engine/shader/shader_compiler.h/.cpp`, `runtime/engine/shader/shader_pipeline.h/.cpp`
> **Depends on**: DXC compiler, shader pipeline infrastructure

## Purpose

The SPIR-V compilation pipeline translates HLSL shaders into Vulkan-compatible SPIR-V bytecode. This occurs automatically and transparently — renderers and demos require **zero code changes** when switching from DX12 to Vulkan. The pipeline integrates with the existing shader compilation cache and hot-reload system.

## Shader Target Selection

The active RHI backend determines the shader output format:

```cpp
enum class ShaderOutputFormat {
    DXIL,     // DX12 backend → DXIL bytecode (SM6.0, SM6.6, SM5.0)
    SPIRV,    // Vulkan backend → SPIR-V bytecode (SM6.0)
    MSL,      // Metal backend → Metal Shading Language (future)
};

// Automatic detection in shader pipeline
ShaderOutputFormat SelectShaderFormat() {
    switch (GetActiveRHIBackend()) {
        case RHIBackend::DX12:    return ShaderOutputFormat::DXIL;
        case RHIBackend::Vulkan:  return ShaderOutputFormat::SPIRV;
        case RHIBackend::Metal:   return ShaderOutputFormat::MSL;
        default:                  return ShaderOutputFormat::DXIL;
    }
}
```

When Vulkan is the active backend, all shader compilation automatically routes through the SPIR-V pipeline.

## DXC Compilation Flags

The DXC compiler is invoked with flags that produce Vulkan-compatible SPIR-V and ensure correct descriptor binding layout:

```cpp
// Pseudo-code: DXC invocation for SPIR-V
DXCCompiler compiler;
std::vector<const wchar_t*> args = {
    // Input/output
    L"-in",  inputPath.c_str(),
    L"-out", outputPath.c_str(),

    // Target format: SPIR-V 1.3 for Vulkan 1.3
    L"-spirv",
    L"-fspv-target-env=vulkan1.3",

    // Shader model: SM6.0 is sufficient for Vulkan
    L"-T", L"ps_6_0",  // or vs_6_0, cs_6_0, etc.

    // Binding shift: Maps HLSL registers to Vulkan descriptor set bindings
    L"-fvk-t-shift",   L"0", L"0",  // t0-t15 → binding 0-15
    L"-fvk-s-shift",   L"16", L"0", // s0-s15 → binding 16-31
    L"-fvk-b-shift",   L"32", L"0", // b0-b15 → binding 32-47

    // Optimization
    L"-O3",

    // Optional: debugging symbols
    // L"-Zi",
};

compiler.Compile(args);
```

## Binding Layout

The flags above map HLSL shader registers to Vulkan descriptor set bindings:

| HLSL Register | Vulkan Binding | Descriptor Type | Capacity | Purpose |
|---|---|---|---|---|
| `t0-t15` | `0-15` | `SAMPLED_IMAGE` | 16 | Texture SRVs |
| `s0-s15` | `16-31` | `SAMPLER` | 16 | Texture samplers |
| `b0-b15` | `32-47` | `UNIFORM_BUFFER` | 16 | Constant buffers (CBVs) |
| Push constants | N/A | `PUSH_CONSTANT` | 128 bytes | Packed data (indices, flags) |

This layout is generated by the `-fvk-*-shift` flags and embedded in the SPIR-V metadata. The Vulkan backend reads this metadata and creates descriptor set layouts to match.

### Example: Texture Access

```hlsl
// HLSL source
Texture2D albedoTex : register(t0);  // Slot t0
SamplerState albedoSampler : register(s0);  // Slot s0

float4 Sample() {
    return albedoTex.Sample(albedoSampler, uv);
}
```

After SPIR-V compilation with the above flags:

```glsl
// Equivalent SPIR-V (conceptual GLSL)
layout(set = 0, binding = 0) uniform sampler2D albedoTex;
layout(set = 0, binding = 16) uniform sampler albedoSampler;

vec4 Sample() {
    return texture(sampler2D(albedoTex, albedoSampler), uv);
}
```

The Vulkan backend's descriptor set layout must match these binding assignments exactly.

## Shader Model Selection

The Vulkan backend targets **SM6.0**, not SM6.6:

| Shader Model | Vulkan Support | Why | Notes |
|---|---|---|---|
| SM5.0 | ✓ Works | DXC can compile to SPIR-V | No wave ops, limited UAVs |
| **SM6.0** | ✓ Works (chosen) | Full feature set, no bindless required | Wave ops, atomics, shared memory |
| SM6.6 | ✓ Works | Bindless via `ResourceDescriptorHeap[]` | **Not used** — see bindless section below |

SM6.0 is sufficient for all rendering needs and simplifies the shader compilation pipeline. The `-T ps_6_0` / `-T vs_6_0` flags specify the target shader model.

### Why Not SM6.6 with Bindless?

SM6.6 bindless (using `ResourceDescriptorHeap[]`) is a DX12-specific pattern. When compiled to SPIR-V with the above binding shifts, the `ResourceDescriptorHeap` array cannot be expressed in Vulkan descriptor semantics — the descriptor indexing patterns differ fundamentally.

Supporting SM6.6 bindless for Vulkan would require:

1. Separate shader source with conditional compilation (`#ifdef VULKAN_BACKEND`)
2. A non-bindless SM6.6 path that still compiles to valid SPIR-V
3. Test coverage for both paths

This violates UzEngine's design principle: **single-source HLSL that compiles to all backends without modification**. Therefore, Vulkan uses the SM5.0-style non-bindless path, even though the SM6.0 target is used.

## Content-Hash Cache Integration

The shader pipeline's content-hash cache automatically incorporates SPIR-V compilation flags:

```cpp
// Content hash includes:
// 1. Source file content (HLSL)
// 2. All #include file contents (recursively)
// 3. Compiler flags (e.g., -spirv, -fvk-t-shift 0 0)
// 4. Active RHI backend

std::string cacheKey = ComputeContentHash(
    source,
    includes,
    compilerFlags,  // ← Changes if -spirv flag is added/removed
    activeBackend   // ← Changes if switching from DX12 to Vulkan
);
```

This ensures that:

- DX12 and Vulkan caches are separate (different flags → different hash)
- Switching backends automatically invalidates relevant caches
- Shader recompilation is deterministic and reproducible

## Compilation Flow

```
Shader Request (demo/renderer)
    │
    ▼
SelectShaderFormat()  ← Checks active RHI backend
    │
    ├─ DX12? → ShaderOutputFormat::DXIL
    └─ Vulkan? → ShaderOutputFormat::SPIRV
    │
    ▼
ComputeContentHash(source, includes, format, flags)
    │
    ▼
CheckCache(hash)
    │
    ├─ Hit? → Return cached bytecode ✓
    │
    └─ Miss? → Compile
        │
        ▼
    if (format == SPIRV) {
        args[] = {..., "-spirv", "-fvk-t-shift 0 0", ...};
    }
        │
        ▼
    DXCCompiler.Compile(args)
        │
        ▼
    WriteCache(hash, bytecode)
        │
        ▼
    Return bytecode
```

## Hot-Reload Behavior

The shader system's hot-reload mechanism (FileWatcher + reverse-dependency graph) works identically for SPIR-V:

1. Shader source file changes on disk
2. FileWatcher detects change, triggers recompile
3. Content hash is recomputed (includes new source)
4. Cache miss → DXC recompiles with SPIR-V flags
5. Reverse dependency graph invalidates all pipelines using this shader
6. Next frame: pipelines recompile with new SPIR-V bytecode

**No special handling required** — the infrastructure treats SPIR-V the same as DXIL.

## DXC Resource Requirements

DXC must be deployed alongside the executable to compile shaders:

```
zig-out/bin/
├── uzengine.exe          (runtime executable)
├── dxcompiler.dll        (DXC compiler)
├── dxil.dll              (DXIL validator)
└── dxclib.lib            (linker import library)
```

For Vulkan shader compilation, both `dxcompiler.dll` and `dxil.dll` are required (DXIL validation is still performed even when generating SPIR-V, as a sanity check on intermediate representation).

## Error Handling

If DXC compilation to SPIR-V fails:

```cpp
// Pseudo-code: error handling
auto result = compiler.Compile(args);
if (!result.IsSuccess()) {
    UZ_LOG(Shader, Error, "SPIR-V compilation failed: {}",
        result.GetErrorMessage());

    // Return invalid shader handle
    return RHIShaderHandle::Invalid();
}
```

The shader system logs the error with full DXC diagnostics (line numbers, error codes) and gracefully degrades by returning an invalid handle. Renderers must guard against invalid shader handles.

## Validation

SPIR-V bytecode output from DXC is **always validated** by `spirv-val` before caching:

```cpp
// Optional: stricter validation
std::vector<uint32_t> spirvWords = bytecodeAsUint32Array(bytecode);

// Validate SPIR-V structure
spirv_val::ValidateModule(spirvWords, validationOptions);
```

This catches malformed bytecode early (at compile time, not at runtime on the GPU).

## Comparison with UE5 and Godot

| Aspect | UE5 | Godot | UzEngine |
|---|---|---|---|
| HLSL → SPIR-V | Custom HLSL→GLSL transpiler | Shader source in GLSL directly | DXC's `-spirv` (clean, standard) |
| Binding layout | Fully automatic via HLSLcc | Manual layout(binding) in GLSL | Automatic via `-fvk-*-shift` flags |
| Shader variants | Per-backend (DXIL, SPIR-V, MSL) | Per-feature (desktop GLSL, Mobile GLSL) | Unified HLSL source, backend-agnostic compilation |
| Cache invalidation | Manual via .sha file | Timestamp-based | Content-hash based (includes flags) |

UzEngine's approach (DXC `-spirv`) is the cleanest: standard compiler flags, no custom transpilers, automatic binding resolution.

## Rules

1. **NEVER** hardcode shader model — always use SM6.0 for Vulkan
2. **ALWAYS** include binding shift flags when compiling to SPIR-V** — `-fvk-t-shift 0 0 -fvk-s-shift 16 0 -fvk-b-shift 32 0`
3. **NEVER** use bindless patterns (`ResourceDescriptorHeap[]`) in shader source intended for Vulkan — stick to SM5.0 non-bindless semantics
4. **ALWAYS** ensure DXC compiler is deployed** — check for `dxcompiler.dll` presence at startup
5. **ALWAYS** validate SPIR-V bytecode** — use `spirv-val` or DXC's validation pass
6. **NEVER** assume shader content hash alone** — include compilation flags and active backend in hash computation
7. **ALWAYS** test hot-reload across backend switches** — modify shader source, verify recompilation works correctly
