# Build Toolchain — Engine Tools

> **Status**: Done (Milestone 1.2)
> **Source**: `runtime/tools/uzembed.cpp`, `runtime/tools/uzengine.cpp`, `runtime/tools/uzcook.cpp`
> **Depends on**: Zig build system, runtime static library

## Purpose

UzEngine ships three command-line tools, all compiled from `runtime/tools/` and linked against `uzengine_runtime.lib`. Each tool has a single, focused responsibility.

## uzembed — Shader Embed Tool

Converts `.hlsl` source files into C++ headers containing `constexpr char[]` literals. This embeds **engine-internal shaders** (debug overlays, grid, fullscreen passes) directly into the compiled binary, eliminating runtime file I/O for core rendering shaders.

### Pipeline

```
shaders/
├── overlay_vs.hlsl
├── overlay_ps.hlsl
├── grid_ps.hlsl
└── debug/
    └── debug_lines_vs.hlsl

        ↓ uzembed --input-dir shaders/ --output-dir build/generated/shaders/

build/generated/shaders/
├── overlay_vs.hlsl.gen.h       → constexpr char kOverlayVS[] = "...";
├── overlay_ps.hlsl.gen.h       → constexpr char kOverlayPS[] = "...";
├── grid_ps.hlsl.gen.h          → constexpr char kGridPS[] = "...";
├── debug/
│   └── debug_lines_vs.hlsl.gen.h
└── engine_shaders.gen.h        → master index (enum + registry + includes)
```

### Generated Index Header

`engine_shaders.gen.h` provides a typed enum and lookup table:

```cpp
// Auto-generated by uzembed — DO NOT EDIT
#pragma once

#include "overlay_vs.hlsl.gen.h"
#include "overlay_ps.hlsl.gen.h"
#include "grid_ps.hlsl.gen.h"

enum class EngineShader {
    OverlayVS,
    OverlayPS,
    GridPS,
    Count
};

struct EngineShaders {
    static const char* GetSource(EngineShader shader);
    static const char* GetName(EngineShader shader);
};
```

### Name Conversion

File names are converted from `snake_case` to `PascalCase`, with shader stage suffixes uppercased:

| File | Constant | Enum |
|------|----------|------|
| `overlay_vs.hlsl` | `kOverlayVS` | `EngineShader::OverlayVS` |
| `overlay_text_ps.hlsl` | `kOverlayTextPS` | `EngineShader::OverlayTextPS` |
| `debug_lines_vs.hlsl` | `kDebugLinesVS` | `EngineShader::DebugLinesVS` |

### Build Integration

uzembed runs **before** the runtime library compiles — `build.zig` establishes this dependency:

```zig
const run_embed = b.addRunArtifact(embed_exe);
run_embed.addArgs(&.{
    "--quiet",
    "--input-dir",  b.path("shaders").getPath(b),
    "--output-dir", b.path("build/generated/shaders").getPath(b),
});

// Runtime compilation depends on uzembed having run
lib.step.dependOn(&run_embed.step);
```

### Why Embed Engine Shaders?

Early in development (POC 0.1), engine shaders were loaded from disk at runtime. This caused a recurring bug: stale shader files in the working directory were used instead of the latest compiled version, leading to hours of debugging "why doesn't my shader change work?" Embedding eliminates this class of bugs entirely.

**Important**: This is for **engine-internal** shaders only (debug overlays, built-in passes). Game/project shaders use the VFS + hot-reload pipeline (section 05).

## uzengine — Standalone Runtime

The main engine executable. Parses CLI arguments, creates a window, initializes the RHI, and runs a render loop. Currently renders an animated clear screen (foundation for scene rendering).

### CLI Arguments

```bash
uzengine [options]

Options:
  --project <path>        Path to .uzproject file
  --width <int>           Window width (default: 1280)
  --height <int>          Window height (default: 720)
  --frames <int>          Number of frames to render (-1 = infinite, default)
  --vsync                 Enable vertical sync
  --no-vsync              Disable vertical sync
  --gpu-breadcrumbs       Enable DRED + GPU breadcrumbs
  --shader-model <sm>     Force shader model (sm5_0, sm5_1, sm6_0, ..., sm6_7)
  --backend <name>        Force RHI backend (dx12, vulkan, metal, null)
```

### Initialization Sequence

```
1. Parse CLI → Config
2. Apply project file overrides (if --project)
3. Re-apply CLI (CLI wins over project file)
4. Initialize logging (console + file sinks)
5. Resolve RHI config (CLI > .uzproject > auto-detect)
6. Create window (Win32 HWND)
7. Create RHI device (DX12Device)
8. Create swap chain (triple-buffered, FLIP_DISCARD)
9. Create command list + fence
10. Enter render loop
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Normal termination (window closed or `--frames` reached) |
| 1 | RHI initialization failure (device/swapchain/command list) |
| 2 | Shader compilation failure |
| 3 | GPU device lost (TDR, driver crash) |

## uzcook — Asset Cook Tool

Batch-imports source assets into engine-native formats, manages a content-addressed cache, and optionally packs everything into a `.uzpak` archive.

### CLI Arguments

```bash
uzcook --source <dir> --output <dir> [--pak <name>] [--verbose]

Options:
  --source <dir>    Directory containing source assets (HLSL, etc.)
  --output <dir>    Output directory for .cache/, .uzimport, .uzpak
  --pak <name>      Pack all cooked assets into <name>.uzpak
  --verbose         Enable debug-level logging
```

### Cook Pipeline

```
1. Scan --source directory for importable files (by extension)
2. For each file:
   a. Check .uzimport sidecar — skip if content hash unchanged
   b. Import via registered importer (ShaderImporter for .hlsl)
   c. Store compiled output in .cache/imported/
   d. Write/update .uzimport sidecar
3. If --pak specified:
   a. Pack all outputs into <name>.uzpak
   b. Generate <name>.uzmanifest
```

### Supported Importers (Current)

| Extension | Importer | Output Format |
|-----------|----------|---------------|
| `.hlsl` | `ShaderImporter` | `.uzshader` (DXIL + SPIR-V bytecode) |

Future importers will handle `.gltf/.glb` (meshes), `.png/.jpg/.exr` (textures), `.wav/.ogg` (audio).

### Incremental Cooking

uzcook uses content-addressed hashing (xxHash64) to avoid re-importing unchanged assets. Each `.uzimport` sidecar stores the content hash of the source file at import time. On subsequent runs, if the hash matches, the asset is skipped.

## Demos

Standalone demos live under `runtime/demos/`, each with its own `build.zig`:

```
demos/
├── clear_screen/     # Animated color cycling (RHI validation)
├── triangle/         # First triangle (PSO + vertex buffer)
├── textured_quad/    # Texture loading + sampling
├── mesh_test/        # .uzmesh cube rendering
├── camera_test/      # Camera controller + projection
└── common/           # Shared utilities across demos
```

Demos link `uzengine_runtime.lib` but are **never** registered in the main `runtime/build.zig`. Each demo is an independent build target — this prevents demo code from polluting the engine library.

## Engine Comparison

| Aspect | UE5 | Godot | UzEngine |
|--------|-----|-------|----------|
| Shader embedding | Yes (USHADERBYTECODE in cooked builds) | GLSL as string literals | **uzembed** (engine shaders as constexpr) |
| Asset cooking | UnrealPak + content browser cook | Resource packer at export | **uzcook** (CLI batch cook) |
| Standalone runtime | `UnrealEditor -game` or shipped executable | `godot --headless` | **uzengine.exe** |
| Demo/sample system | Sample projects (separate repo) | `tests/` + GDScript examples | `demos/` with standalone `build.zig` |

## Rules

1. **NEVER embed game shaders** — only engine-internal shaders go through uzembed. Game shaders use VFS + hot-reload
2. **NEVER register demos in `runtime/build.zig`** — each demo is standalone with its own build
3. **ALWAYS use exit codes consistently** — 0=success, 1=render, 2=shader, 3=device lost
4. **ALWAYS support `--verbose` in tools** — debug-level logging must be one flag away
5. **ALWAYS re-apply CLI after loading project file** — CLI arguments must take precedence
