# Optimization Systems Spec

## Overview

Optimization in UzEngine is a first-class feature, not an afterthought. Real production MMO and open-world games consistently fail not due to missing features but due to cumulative performance debt accumulated from unoptimized assets and poor engine defaults. Every system that can cause a draw call spike, a VRAM overflow, or a physics simulation meltdown must have a sensible default and a clear upgrade path.

This spec addresses nine categories of optimization that have caused measurable pain in production game development using other engines (particularly Unreal Engine 4/5). Each section describes the problem, the UzEngine solution, and the API surface exposed to developers and tools.

The philosophy is: **make the correct thing the default thing**. LODs should exist unless you opt out. sRGB should be correctly detected rather than blindly applied. Decorative UI elements should never catch input. Physics objects that should not exist should not be created.

## 1. Auto-LOD Pipeline

### Problem

In Unreal Engine, LODs are not generated by default for static meshes. Artists import a 500K-triangle hero asset and ship it at full resolution for every draw distance. A scene with 200 unique static props at full resolution pushes millions of triangles onto the GPU for objects covering two pixels on screen. The fix (manually configuring LODs per mesh) is tedious and frequently skipped under deadline pressure.

### Solution

At import time, UzEngine automatically generates 4 LOD levels for every `.fbx` and `.glb` static mesh using **meshoptimizer**. The behavior is controlled by the `.import.json` sidecar file. The default is `auto_lod: true`. Developers can disable this only by explicitly setting `auto_lod: false`.

### LOD Generation Algorithm

```
Input: base mesh (LOD0), vertex count V, index count I

LOD1: meshopt_simplify(target=I*0.50, error_threshold=0.01)
LOD2: meshopt_simplify(target=I*0.25, error_threshold=0.05)
LOD3: meshopt_simplify(target=I*0.10, error_threshold=0.15)

After each simplification:
  meshopt_optimizeVertexCache(lod_indices)
  meshopt_optimizeOverdraw(lod_indices, threshold=1.05)
  meshopt_optimizeVertexFetch(lod_indices)
```

The `error_threshold` values are in normalized mesh space (0 = no error, 1 = allow destroying the mesh). Values above 0.15 create visually unacceptable LOD3 levels for most meshes; the importer clamps to 0.15 max.

### Screen-Size Thresholds

LOD is selected by projected screen coverage, not world-space distance. This keeps LOD behavior consistent regardless of camera FOV:

```
screen_coverage = mesh_bounding_sphere_radius / (view_distance * tan(fov_half))

coverage > 0.50  -> LOD0  (full detail, fills half screen or more)
coverage > 0.25  -> LOD1  (medium shot)
coverage > 0.10  -> LOD2  (background object)
coverage > 0.02  -> LOD3  (distant, barely visible)
coverage <= 0.02 -> cull  (below visibility threshold)
```

Thresholds are configurable per mesh via `lod_screen_sizes` in `.import.json`.

### Nanite Fallback

For meshes with triangle count exceeding 100,000, the importer sets `nanite_fallback: true` in `.import.json` by default if the `phase4-nanite-virtual-geometry` system is available. When Nanite is active, the cluster LOD system overrides the traditional 4-level LOD and LOD0 becomes the virtual geometry cluster DAG. For all meshes under 100K triangles, traditional 4-level LOD is used (Nanite overhead is not worth it for small meshes).

### Import Settings (`.import.json`)

```json
{
  "source":  "assets/meshes/rock_large.fbx",
  "type":    "StaticMesh",
  "settings": {
    "auto_lod":          true,
    "lod_screen_sizes":  [0.50, 0.25, 0.10, 0.02],
    "lod_error_thresholds": [0.0, 0.01, 0.05, 0.15],
    "nanite_fallback":   false,
    "nanite_threshold_triangles": 100000
  }
}
```

Setting `auto_lod: false` disables LOD generation entirely. The mesh ships with only LOD0. This should be used only for meshes that are always close to camera (first-person weapon, UI elements in world space).

### VSCode Editor Integration

The Asset Browser shows LOD triangle counts per level in the mesh inspector:
```
rock_large.uzmesh
  LOD0: 48,200 tris (screen > 50%)
  LOD1: 24,100 tris (screen > 25%)
  LOD2: 12,050 tris (screen > 10%)
  LOD3:  4,820 tris (screen > 2%)
  [Regenerate LODs] [Override Thresholds]
```

## 2. Texture Optimization and Bulk Tools

### Problem

Third-party asset packs (bought from marketplaces, downloaded from Quixel, exported from Substance) typically contain uncompressed PNGs at 4096x4096 with no mips. A single asset pack can push 2+ GB of VRAM before any compression. Artists need tools to mass-import and convert without touching each file individually.

### Solution

The VSCode extension provides a **Bulk Texture Optimizer** panel that operates on a folder selection. The panel applies format detection, sRGB auto-detection (see Section 3), generates mip chains, and runs BC7/BC5/BC4 compression in parallel across all CPU threads.

## 3. sRGB Auto-Detection System

### Problem

Unreal Engine 4 and 5 mark textures as sRGB by default. This is correct for albedo/diffuse maps but catastrophically wrong for normal maps, roughness maps, metallic maps, and AO maps. A roughness texture interpreted as sRGB gets gamma-expanded, producing values of 0.2 that read as 0.73, completely destroying PBR lighting. This bug is common, visually subtle (surfaces look slightly off), and time-consuming to diagnose.

Substance Painter exports follow strict naming conventions that map directly to sRGB vs. linear. UzEngine's importer uses these conventions as the primary detection signal.

### Filename Pattern Detection

The following patterns are matched case-insensitively against the base filename (without extension):

#### sRGB = TRUE (gamma-encoded, needs sRGB conversion on read)

```
Patterns: albedo, diffuse, basecolor, base_color, col, color, _d (suffix)
Examples: hero_albedo.png, body_Diffuse.png, skin_BaseColor.png
```

#### sRGB = FALSE (linear data, must NOT be gamma-corrected)

```
Patterns: normal, nrm, nor, normalmap, bump,
          roughness, rough, rgh,
          metallic, metal, met,
          ao, ambient_occlusion, occlusion, cavity,
          height, displacement, disp,
          emissive, emit, glow,
          mask, opacity, alpha,
          packed, orm, rma
Examples: rock_Normal.png, skin_Roughness.png, armor_Metallic.png
```

When multiple patterns match (e.g., a file named `hero_albedo_color.png`), the first match in the priority list wins. The priority list is: explicit `.import.json` override > filename pattern > alpha-channel analysis > fallback (sRGB=true).

### Alpha-Channel Analysis

When the sRGB determination from filename is ambiguous (no known pattern matched), the importer reads the image and checks the alpha channel:

```cpp
bool analyze_alpha(const Image& img) {
    // Scan all pixels; if all alpha values are 255 → no meaningful alpha
    for (uint32_t y = 0; y < img.height; ++y) {
        for (uint32_t x = 0; x < img.width; ++x) {
            if (img.pixel(x, y).a < 255) return true;  // has meaningful alpha
        }
    }
    return false;  // no alpha content, mark has_alpha: false
}
```

The alpha analysis result is stored in `.import.json` as `has_alpha: bool`. Textures with `has_alpha: false` can skip the alpha channel entirely and be packed into BC4 instead of BC7, saving 50% VRAM.

### Substance Painter Convention Mapping

Substance Painter 9.x default export presets use the following suffixes:

| Substance Painter Suffix | UzEngine Detection | Format |
|-------------------------|-------------------|--------|
| `_BaseColor` | sRGB=true | BC7 SRGB |
| `_Normal` | sRGB=false | BC5 UNORM |
| `_Roughness` | sRGB=false | BC4 UNORM |
| `_Metallic` | sRGB=false | BC4 UNORM |
| `_AmbientOcclusion` | sRGB=false | BC4 UNORM |
| `_Emissive` | sRGB=false | BC7 UNORM |
| `_Opacity` | sRGB=false | BC4 UNORM |
| `_Height` | sRGB=false | BC4 UNORM |

This mapping is also used when importing Unity-exported assets (Unity uses identical conventions).

### Import.json Storage

```json
{
  "source":   "textures/hero_BaseColor.png",
  "type":     "Texture",
  "settings": {
    "format":          "BC7_UNORM_SRGB",
    "srgb":            true,
    "srgb_source":     "filename_pattern",
    "has_alpha":       false,
    "mip_filter":      "box",
    "max_size":        4096
  }
}
```

`srgb_source` can be: `"filename_pattern"`, `"alpha_analysis"`, `"user_override"`, `"fallback"`. This lets artists quickly audit why the engine chose a particular sRGB setting.

### VSCode Override UI

In the texture inspector, a warning badge appears when `srgb_source` is `"fallback"` or `"alpha_analysis"` (the engine was uncertain). The artist can confirm or override with one click, which writes `srgb_source: "user_override"` to `.import.json`.

## 4. Modular Skeleton Merging

### Problem

In MMO and RPG games, player characters and NPCs wear equipment from different meshes (head, torso, legs, boots, gloves, pauldrons) all sharing one underlying base skeleton. Unreal Engine handles this with the `SetMasterPoseComponent` API: all slave meshes reference the master mesh for its evaluated bone transforms. This works but has limitations: bone counts must match exactly, equipment swaps require reattaching master-slave relationships, and with thousands of NPCs the overhead adds up.

In a typical MMO zone with 200 visible players, each wearing unique equipment combinations, unoptimized skeleton handling produces 200 * 6 = 1200 separate `AnimateSkeletalMesh` calls per frame.

### Solution: MergedSkeletonComponent

`MergedSkeletonComponent` is an ECS component that takes N `CSkeletalMesh` component handles sharing a base skeleton and executes a single GPU skinning pass that writes combined output for all equipment pieces.

### Component Definition

```cpp
// src/engine/components/merged_skeleton.h

struct CMergedSkeleton {
    Handle<Skeleton>    base_skeleton;        // shared base skeleton asset
    uint32_t            equipment_count;      // number of equipment pieces (max 8)
    Handle<SkeletalMesh> equipment[8];         // individual equipment meshes
    Handle<Material>    equipment_material[8]; // per-piece material
    BoneRemapTable      remap[8];             // bone index remapping per piece

    // Updated each frame after animation evaluation
    GpuBuffer*          bone_palette;         // StructuredBuffer<float4x4[256]>
};
```

### Bone Remapping

Equipment meshes may have a subset of the base skeleton's bones. The `BoneRemapTable` maps equipment bone indices to base skeleton bone indices:

```cpp
struct BoneRemapTable {
    uint16_t count;           // number of bones in equipment mesh
    uint16_t remap[256];      // equipment_bone[i] → base_bone[remap[i]]
};
```

At import time, the importer computes the remap table by matching bone names between the equipment mesh skeleton and the base skeleton. Missing bones are mapped to the identity matrix.

### GPU Skinning Pass

The merged skeleton executes one GPU skinning compute dispatch:

```hlsl
// shaders/skinning/merged_skinning.hlsl

[numthreads(64, 1, 1)]
void CSMergedSkin(uint3 id : SV_DispatchThreadID) {
    uint vertex_id = id.x;
    uint piece_id  = id.y;  // equipment piece

    if (vertex_id >= g_PieceCounts[piece_id]) return;

    uint base_offset = g_PieceVertexOffsets[piece_id];
    Vertex v = g_InputVertices[base_offset + vertex_id];

    // Skin using 4 bone influences
    float4x4 skin_matrix =
        g_BonePalette[g_Remap[piece_id][v.bone_idx[0]]] * v.bone_weight[0] +
        g_BonePalette[g_Remap[piece_id][v.bone_idx[1]]] * v.bone_weight[1] +
        g_BonePalette[g_Remap[piece_id][v.bone_idx[2]]] * v.bone_weight[2] +
        g_BonePalette[g_Remap[piece_id][v.bone_idx[3]]] * v.bone_weight[3];

    g_OutputVertices[base_offset + vertex_id].pos =
        mul(skin_matrix, float4(v.pos, 1.0)).xyz;
    g_OutputVertices[base_offset + vertex_id].normal =
        normalize(mul((float3x3)skin_matrix, v.normal));
}
```

### Equipment Swap API

Equipment swaps do not require skeleton re-evaluation. The `CMergedSkeleton` component is updated directly:

```lua
-- Lua equipment swap (e.g., player equips new chest armor)
local merged = ctx.entity:get_component("CMergedSkeleton")

-- Swap chest slot (index 1 = torso)
ctx.character:attach_equipment(entity, {
    slot   = "torso",
    mesh   = ctx.assets:load("res://equipment/chest_plate.uzmesh"),
    material = ctx.assets:load("res://materials/armor_steel.uzmat")
})
```

```cpp
// C++ equivalent
void CharacterSystem::attach_equipment(EntityId id, EquipSlot slot,
                                        Handle<SkeletalMesh> mesh,
                                        Handle<Material> mat) {
    auto& merged = ecs.get<CMergedSkeleton>(id);
    uint32_t idx = slot_to_index(slot);
    merged.equipment[idx]          = mesh;
    merged.equipment_material[idx] = mat;
    merged.remap[idx] = BoneRemapper::compute(mesh->skeleton, merged.base_skeleton);
    // No skeleton rebuild required; remap recalculated and GPU palette updated next frame
}
```

### Performance

For 200 NPCs each with 6 equipment pieces:
- Traditional: 1200 GPU skinning dispatches per frame
- MergedSkeletonComponent: 200 dispatches per frame (one per character, all pieces in one pass)
- Reduction: 6x fewer GPU dispatches for skinning

## 5. Material Merging and Texture Atlasing

### Problem

A city environment with 500 unique prop meshes (benches, mailboxes, trash cans, fences, fire hydrants) each using a unique material means 500+ draw calls per frame from those props alone, even with GPU instancing active (instancing only batches identical mesh+material pairs). The props share the same PBR shader but have different texture content.

### Solution: MaterialMerger

`MaterialMerger` is a build-time tool (invoked from VSCode or the asset pipeline CLI) that:
1. Groups static meshes by shader type
2. Packs their textures into a shared atlas (up to 4096x4096)
3. Remaps UV coordinates to atlas sub-regions
4. Emits a merged `.uzmesh` with a single `.uzmat` referencing the atlas

The merged result is a **new asset** — the originals are not modified. The merger generates `_merged` suffixed outputs.

### Atlas Packing

```
Atlas layout (4096x4096):
┌──────┬──────┬──────┬──────┐
│ prop │ prop │ prop │ prop │  row 0: 1024x1024 textures
│  A   │  B   │  C   │  D   │
├──────┴──────┬──────┴──────┤
│    prop E   │    prop F   │  row 1: 2048x1024 textures
│  (2048x1024)│  (2048x1024)│
├─────────────┴─────────────┤
│          prop G           │  row 2: 4096x1024 wide texture
│        (4096x1024)        │
└───────────────────────────┘
```

Packing algorithm: **Guillotine rectangle packer** (O(N log N), produces near-optimal packing for power-of-two textures). Textures are sorted largest-first before packing.

### UV Remapping

Each vertex's UV is remapped from [0,1] space to the atlas sub-region:

```cpp
// UV remapping during atlas generation
vec2 remap_uv(vec2 original_uv, AtlasRegion region) {
    return region.uv_min + original_uv * (region.uv_max - region.uv_min);
}
```

The remapper bakes the new UVs directly into the merged `.uzmesh` vertex buffer. No runtime UV transform is needed.

### Merge Criteria

Meshes are eligible for merging when:
1. Same shader variant key (same PBR shader, same defines)
2. All textures are the same format and same or smaller than 1024x1024 (textures above 1024 are unlikely to pack efficiently)
3. All meshes are static (no skeletal mesh, no morph targets)
4. Total atlas texture count <= 16 (configurable)

### Output

```
MaterialMerger::merge("res://scenes/city_props/") produces:
  city_props_merged.uzmesh    (merged geometry, remapped UVs)
  city_props_merged_albedo.dds  (atlas: all albedo textures packed)
  city_props_merged_normal.dds  (atlas: all normal textures packed)
  city_props_merged_orm.dds     (atlas: packed ORM)
  city_props_merged.uzmat       (one material referencing all 3 atlas textures)

Result: 500 draw calls → 1 draw call (or ~handful with LOD splits)
```

### IPC Handler

```
asset.mergeAtlas { meshes[], atlas_size?, output_name }
    -> { ok, output_mesh, output_material, draw_call_reduction }
```

## 6. UI Pointer Events and Input Passthrough

### Problem

In Unreal Engine's UMG Widget system, images (UImage) are interactive by default. This means a decorative background image in a menu panel catches click events, silently swallowing input intended for buttons underneath it. The fix in UMG is to manually set `Visibility = HitTestInvisible` on every decorative element. This is easy to forget and produces invisible, hard-to-diagnose input bugs.

In a complex inventory UI with 50+ decorative elements, forgetting even one `HitTestInvisible` setting causes an unresponsive button that passes QA but fails in player hands.

### Solution: Default Non-Interactive Policy

The `uz_ui_html.dll` layout engine enforces the following policy:

**By default, all elements are non-interactive** (`pointer-events: none`) unless they are intrinsically interactive or explicitly marked.

### Interactive by Default (whitelist)

The following element types receive pointer events by default:
- `<button>`
- `<a href="...">`
- `<input>`, `<textarea>`, `<select>`
- Any element with `[data-interactive]` attribute
- Any element with `cursor: pointer` in computed style
- Any element with `onclick`, `onmousedown`, `ontouchstart` event handlers

### Non-Interactive by Default (enforced)

```html
<!-- WRONG: this div will NOT catch clicks (correct behavior) -->
<div class="background-panel">
  <button onclick="close()">Close</button>  <!-- this WILL catch clicks -->
</div>

<!-- CORRECT: explicit opt-in for a div that needs to handle drag -->
<div data-interactive class="drag-handle">Drag me</div>
```

### Layout Engine Enforcement

Inside `uz_ui_html.dll`, the CSS property `pointer-events` is parsed but **the default resolved value is `none`**, not `auto`. The CSS property must be explicitly set to `auto` or `all` to enable hit-testing on a non-interactive element:

```css
/* Enable pointer events on a specific decorative div that needs drag support */
.drag-panel {
    pointer-events: auto;
    cursor: grab;
}
```

### Linter Warnings

The VSCode UzEngine extension's HTML linter emits warnings for:

1. `<img>` with `onclick` attribute and no `cursor: pointer` in inline style — likely unintentional.
2. Any element with `pointer-events: auto` and no interactive child or no event handler — dead event capture zone.
3. Semi-transparent overlay `<div>` elements without `pointer-events: none` — likely blocking elements behind them.

Warning example:
```
[UzUI Lint] ui/inventory.html:47 — <div class="slot-background">
  has no interactive children and no event handler.
  Add pointer-events: none or data-interactive to clarify intent.
```

### Lua API

```lua
-- Enable interaction on a dynamically created element
ctx.ui:set_interactive(element, true)   -- adds pointer-events: auto
ctx.ui:set_interactive(element, false)  -- adds pointer-events: none (default)
```

## 7. Open-World Culling Stack

### Problem

In open-world games (forests, cities, large landscapes), frustum culling and HZB occlusion culling alone are insufficient. A forest with 50,000 trees in the frustum is invisible from a distance at full polygon resolution. Without a multi-stage culling pipeline, rendering such scenes at 60fps is impossible.

### Solution: Layered Culling Pipeline

UzEngine processes visibility through six ordered stages:

```
Visibility Pipeline (per frame):
  1. Frustum Cull          → removes off-screen entities
  2. HZB Occlusion Cull    → removes occluded entities (GPU, async)
  3. Distance Cull          → removes entities beyond absolute max distance
  4. Impostor Swap          → replaces distant meshes with billboards
  5. Foliage Density LOD    → reduces foliage density at distance
  6. LOD Select             → picks LOD level for surviving entities
```

### Distance Cull

Every entity can have a `CCullDistance` component:

```cpp
struct CCullDistance {
    float cull_distance_world;  // entity removed beyond this distance
    float fade_start_factor;    // begin fade at (cull_distance * factor), default 0.8
};
```

Foliage entities (grass, small rocks) use low cull distances (30-50m). Hero assets use higher values (500m+). Without this component, entities are never distance-culled (not appropriate for hero props).

### Impostor Billboard System

At distance thresholds above LOD3 but below cull distance, the **Impostor** system replaces the 3D mesh with a pre-baked billboard quad facing the camera.

**Impostor Generation (build time)**:

```
for each static mesh with impostor_enabled: true:
    for angle in [0°, 45°, 90°, 135°, 180°, 225°, 270°, 315°]:
        render mesh to 256x256 render target from above angle
        capture albedo + alpha + normal
    pack 8 renders into impostor atlas (2048x256 strip)
    save impostor_atlas.dds
```

**Impostor Rendering (runtime)**:

The impostor renderer selects the two closest capture angles and blends between them based on the current view angle. The billboard quad always faces the camera (cylindrical billboard for trees, spherical for bushes):

```hlsl
// impostor.hlsl
float angle_to_camera = atan2(camera_dir.z, camera_dir.x);
float normalized = (angle_to_camera + PI) / (2.0 * PI);  // [0, 1]
uint frame_a = uint(normalized * 8.0) % 8;
uint frame_b = (frame_a + 1) % 8;
float blend = frac(normalized * 8.0);

float2 uv_a = uv_for_frame(v.uv, frame_a);
float2 uv_b = uv_for_frame(v.uv, frame_b);
float4 color = lerp(g_ImpostorAtlas.Sample(s, uv_a),
                    g_ImpostorAtlas.Sample(s, uv_b), blend);
```

### Import Setting

```json
{
  "source": "assets/meshes/oak_tree.fbx",
  "type":   "StaticMesh",
  "settings": {
    "auto_lod":         true,
    "impostor_enabled": true,
    "impostor_distance": 80.0,
    "impostor_resolution": 256,
    "cull_distance":    500.0
  }
}
```

### Foliage Density LOD

Foliage (grass tiles, rock clusters) reduce instance density as distance increases:

```
Distance < 20m:   100% instances rendered (full mesh)
Distance 20-40m:  50% instances (LOD1)
Distance 40-60m:  billboard impostor for each cluster
Distance > 60m:   no foliage rendered
```

Density reduction uses a deterministic hash to choose which instances to drop at each distance tier, ensuring no visible popping:

```cpp
bool should_render_at_distance(uint32_t instance_id, float distance, float threshold) {
    float hash = hash_float(instance_id) * threshold;
    return distance < hash;
}
```

### Per-Instance Visibility

GPU instancing passes include a visibility mask in the per-instance data:

```hlsl
struct InstanceData {
    float4x4 transform;
    float    lod_fade;      // 0.0 = hidden, 1.0 = fully visible
    uint     flags;         // bit0=impostor_active, bit1=shadow_only
};
```

This allows per-instance fade-in/out when transitioning between full mesh and impostor without CPU involvement.

## 8. Proximity LOD Swap System (MMO Pattern)

### Problem

In MMO games, the world is populated with harvestable resources (trees, ore nodes, herbs), interactive environmental props (doors, chests, switches), and wildlife. When 500 trees are on screen simultaneously, full physics simulation for all 500 trees (collision capsules, interaction volumes, trigger zones, server sync) would consume enormous CPU and network budget.

The correct optimization is: render trees as instanced GPU meshes with no physics or interaction at distance. Only when a player is within interaction range (say, 5 meters) does the full interactive component (collision, server sync, loot table) activate.

### Solution: ProximitySwapComponent

```cpp
// src/engine/components/proximity_swap.h

struct CProximitySwap {
    // Distance radii
    float  inner_radius;         // <= this: INTERACTIVE mode (full mesh + collision)
    float  outer_radius;         // > this: DISTANT mode (GPU instance, no collision)

    // State
    enum class State : uint8_t {
        DISTANT     = 0,   // GPU instanced, no collision, no server sync
        APPROACHING = 1,   // transition zone, loading interactive data
        INTERACTIVE = 2    // full mesh, collision active, server sync active
    };
    State current_state;

    // Server validation hook (optional, for MMO server-authoritative state)
    // Called when transitioning APPROACHING -> INTERACTIVE
    using ServerValidateFn = std::function<void(EntityId, std::function<void(bool)>)>;
    ServerValidateFn server_validate;

    // Assets
    Handle<StaticMesh>   distant_mesh;     // GPU instanced mesh used in DISTANT
    Handle<SkeletalMesh> interactive_mesh; // full mesh used in INTERACTIVE
    Handle<Material>     material;
};
```

### State Machine

```
State: DISTANT
  Conditions: player distance > outer_radius
  Rendering: GPU instanced (no collision, no trigger volume, no server sync)
  Action on exit: begin async load of interactive_mesh if not loaded

State: APPROACHING
  Conditions: inner_radius < player distance <= outer_radius
  Rendering: switch to interactive_mesh (but collision still inactive)
  Action: call server_validate(entity, callback)
         if callback(true): transition to INTERACTIVE
         if callback(false): stay in APPROACHING

State: INTERACTIVE
  Conditions: player distance <= inner_radius AND server validated
  Rendering: interactive_mesh, collision active, trigger volume active, server sync active
  Action on exit: deactivate collision, deactivate triggers, return to APPROACHING
```


### Lua Integration

```lua
-- server validate callback (game.dll or Lua)
function game.harvest_tree_validate(entity_id, respond)
    -- Ask server if this node is available
    ctx.net:rpc("query_resource_state", entity_id, function(available)
        respond(available)
    end)
end

-- When player enters INTERACTIVE state

    local resource = ctx.entity:get_component(entity, "CResourceNode")

        ctx.events:emit("harvest.begin", entity)

end)
```

### Performance Impact

For a zone with 5,000 harvestable nodes:
- DISTANT (4,990 nodes): 0 collision shapes, 0 trigger volumes, 0 server syncs, ~5 GPU instanced draw calls total (all share the same lod3 mesh)
- INTERACTIVE (10 nodes): 10 full collision shapes, 10 trigger volumes, 10 server sync channels
- CPU physics cost: reduced from O(N=5000) to O(N=10) for the interaction layer

## 9. Companion and Mount No-Collision Pattern

### Problem

Pets and mounts in MMOs are entities that visually follow their owner. In Unreal, these are typically spawned as pawns with full physics capsule colliders. This causes several well-known bugs:
1. The pet's capsule collides with the player's capsule, creating jitter or stacking.
2. The pet blocks the player's ability to walk through doorways.
3. Pathfinding treats the pet as an obstacle.
4. Other players' pets collide with yours, creating chaos in crowded towns.

The fix is well-known: pets and mounts should have no collision geometry whatsoever. They are visual-only entities that occupy no physics space.

### Solution: CCompanion Flag

The `CCompanion` component marks an entity as a companion entity (pet, mount, summon, familiar). The presence of this component enforces:

1. **No CCollider shapes created**: The physics system skips `CCollider` shape registration for entities with `CCompanion`.
2. **COMPANION collision layer**: The entity is assigned to the `COMPANION` collision layer, which is excluded from all standard query layers (player movement, projectile, trigger).
3. **Owner-only interaction**: Only entities with the same `owner_id` in their `CCompanion` component can receive interaction events from this entity.

### Component Definition

```cpp
// src/engine/components/companion.h

struct CCompanion {
    EntityId owner_id;           // the owning entity (player, NPC)
    CompanionType type;          // PET, MOUNT, SUMMON, FAMILIAR

    enum class CompanionType : uint8_t {
        PET     = 0,   // follows owner, decorative
        MOUNT   = 1,   // player rides, controls locomotion
        SUMMON  = 2,   // combat summon, may have its own AI
        FAMILIAR = 3   // shoulder pet, purely cosmetic
    };

    bool allow_collision_with_owner;  // default: false
                                       // set true only for mounts (player stands on it)
};
```

### Collision Layer Configuration

In `.uzproj`:

```toml
[physics.collision_layers]
# Standard layers
DEFAULT   = 0x0001
PLAYER    = 0x0002
PROJECTILE = 0x0004
TRIGGER   = 0x0008
TERRAIN   = 0x0010
NPC       = 0x0020
COMPANION = 0x0040    # companions — excluded from all other layers by default

[physics.layer_matrix]
# COMPANION interacts with nothing by default
COMPANION.collides_with = []
# Exception: MOUNT type companions interact with PLAYER (so player can mount)
# This is handled at entity spawn time, not in the layer matrix
```

### Physics System Integration

```cpp
// src/engine/systems/physics_system.cpp

void PhysicsSystem::register_entity(EntityId id) {
    if (ecs.has<CCompanion>(id)) {
        // Skip all collision shape creation
        LOG_DEBUG("Entity {} is CCompanion — no collision shapes created", id);
        return;  // early return, no physics body
    }

    // Standard registration: create body, add shapes, configure layers
    create_physics_body(id);
}
```


### Validation Warning

The asset validator emits a warning (not an error) if a companion entity has a `CCollider` or `CRigidBody` component:

```

  This is almost always wrong. Companion entities should have no collision geometry.
  To suppress this warning: add suppress_companion_collision_warning: true to CCompanion.
```
