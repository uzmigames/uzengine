## 1.5.0 — Physics

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | Chaos Physics (proprietary) | Custom engine replacing PhysX. Async stepping on task graph. `FChaosScene` per level. Fixed substep with configurable min/max dt and max substeps. Destruction system built-in (GC — Geometry Collection). |
| **Godot 4.x** | Jolt Physics | Replaced Godot Physics with Jolt (4.4+). `PhysicsServer3D` abstract → `JoltPhysicsServer3D`. Custom `JoltJobSystem` bridges to Godot's `WorkerThreadPool`. RID-based handles. Fixed 60Hz. |
| **Unity 6** | PhysX (classic) / Havok (DOTS) | PhysX 4.x for MonoBehaviour. Unity Physics (stateless, deterministic) or Havok (stateful, stable) for DOTS ECS. `FixedStepSimulationSystemGroup` at 1/60s. Burst-compiled collision detection. |

**UzEngine**: **Jolt Physics** — MIT license, faster than PhysX in benchmarks, deterministic (critical for networking), already validated by Godot at scale. Integrate Jolt's job system with our task graph. Fixed 60Hz, configurable substeps. RID-based handles for ownership safety.

```cpp
// Physics world integration
PhysicsWorld world;
auto body = world.CreateRigidBody(RigidBodyDesc{
    .shape = BoxShape(Vec3(1, 1, 1)),
    .mass = 10.0f,
    .type = BodyType::Dynamic,
    .position = Vec3(0, 10, 0)
});

// Raycasting
HitResult hit;
if (world.Raycast(origin, direction, maxDist, hit)) {
    // hit.entity, hit.position, hit.normal, hit.distance
}
```

**VHACD** for automatic convex decomposition of complex meshes into collision shapes.

## 1.5.1 — Animation

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | `UAnimInstance` + AnimGraph | Skeletal mesh with `USkeleton`. AnimGraph (node-based state machine in Blueprint). Blend spaces (1D/2D), montages (one-shot overlays), control rig (IK, procedural). GPU skinning via compute shader. Root motion via `FRootMotionSource`. Additive layers. Animation notifies (events at keyframes). |
| **Godot 4.x** | `AnimationPlayer` + `AnimationTree` | `Skeleton3D` + `AnimationPlayer` for simple playback. `AnimationTree` for state machines and blend trees. `AnimationNodeBlendSpace2D` for locomotion. Root motion via `root_motion_position/rotation`. CPU skinning (GPU skinning added 4.4+). |
| **Unity 6** | Animator + Mecanim / DOTS Animation | `Animator` controller (state machine). `BlendTree` for blending. `AvatarMask` for layered animation. Root motion via `applyRootMotion`. GPU skinning. DOTS Animation (in development) for ECS-based batched evaluation. Retargeting via Avatar system. |

**UzEngine**: GPU skinning via compute shader (like UE5). `.uzskeleton` (JSON), `.uzanimsequence` (JSON header + binary keyframes). State machine and blend tree as `.uzanimcontroller` (JSON). Montages, additive layers, root motion, animation events. FABRIK + CCD IK for control rig.

## 1.5.2 — Audio

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | Custom AudioMixer | Submix hierarchy (Main → SFX/Music/Voice/Reverb). Separate audio render thread. `FQuartzClockManager` for quantized events. Sound cues (node graph). Reverb volumes. Distance attenuation curves. |
| **Godot 4.x** | Custom AudioServer | `AudioDriver` for platform I/O. `AudioStreamPlayer3D` with distance attenuation. Audio buses (submix equivalent). Per-bus effects (reverb, EQ, compressor). |
| **Unity 6** | FMOD-based internal | `AudioSource`/`AudioListener`. AudioMixer with groups. Spatial blend (2D↔3D). Reverb zones. Third-party: FMOD Studio or Wwise for AAA audio. |

**UzEngine**: **miniaudio** (backend) + custom submix mixer. miniaudio handles cross-platform device abstraction (single header, public domain). Custom submix hierarchy: Main → SFX / Music / Voice / Reverb. Separate audio thread (never block game thread). Spatial audio with distance attenuation, HRTF, reverb zones. Codecs: OGG (Vorbis), WAV, MP3 (dr_libs), Opus.

## 1.5.3 — Navigation & AI

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | Recast/Detour + custom AI | `ANavigationData` → `ARecastNavMesh`. `UNavigationSystemV1` manages navmesh generation. `UAITask_MoveTo` for pathfinding. Behavior trees (`UBehaviorTree`, `UBTTask_*`). EQS (Environment Query System) for spatial AI queries. AI perception (sight cones, hearing radius). Blackboard for state. |
| **Godot 4.x** | Recast/Detour + custom AI | `NavigationServer3D` wraps Recast/Detour. `NavigationAgent3D` for pathfinding. No built-in behavior trees (community addons). No EQS. |
| **Unity 6** | NavMesh + ML-Agents | `NavMesh` (Recast-based). `NavMeshAgent` for pathfinding. `NavMeshObstacle` for dynamic obstacles. No built-in behavior trees (third-party: NodeCanvas, Behavior Designer). ML-Agents for reinforcement learning AI. |

**UzEngine**: **Recast/Detour** for navmesh (used by all 3 engines). **RVO2** for crowd avoidance. Behavior trees with JSON definition (`.uzbehavior` — tasks, decorators, services, blackboard). EQS-style queries ("find cover", "find flanking position"). Perception system (sight cones, hearing radius). All AI data is JSON — LLM can generate and modify behavior trees.

## 1.5.4 — Scripting

> **Status: COMPLETE** — LuaJIT 2.1 integration fully implemented as of phase0-0.8.0.

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | C++ + Blueprints | C++ for performance. Blueprints (visual scripting) for gameplay. `UCLASS`/`UPROPERTY`/`UFUNCTION` macros + UHT code generation for reflection. Hot-reload via Live Coding (incremental link). Game DLLs. |
| **Godot 4.x** | GDScript + C++ (GDExtension) + C# | GDScript (Python-like, editor-integrated). GDExtension for native C/C++ plugins. C# via Mono/.NET (optional). Hot-reload for GDScript (instant). |
| **Unity 6** | C# (Mono / IL2CPP) | C# for everything. Managed runtime with GC. IL2CPP for AOT compilation in builds. Hot-reload via domain reload (slow, ~3-5s). Assembly definitions for compilation boundaries. |

**UzEngine**: **C++ (primary)** + **Lua (secondary)**. No visual scripting in Phase 1 (deferred to 2.3 as "Visual Script Editor").

- **C++ game DLL**: `UZ_REGISTER_MODULE()` macro for component registration. Hot-reload via serialize → unload DLL → rebuild → reload → deserialize. No UHT/code generation — simpler than Unreal.
- **LuaJIT 2.1**: Embedded, sandboxed. Bound to engine API (scene, input, physics, audio). Hot-reload via file watcher (instant, no restart). For rapid prototyping and mod support.

Both are well-represented in LLM training data — LLMs can generate both C++ and Lua game logic.

### UzEngine Implementation (Complete)

**Core infrastructure** (`runtime/engine/scripting/`):

- `LuaVM` — singleton managing the LuaJIT 2.1 state. Sandboxed: `os.execute`, `io.open`, `load`, and `require` are disabled to prevent untrusted script access to the filesystem and OS.
- `LuaScriptInstance` — per-entity script instance with three lifecycle hooks: `on_start`, `on_update`, `on_stop`. Bound to an ECS entity at creation.
- `ScriptSystem` / `ScriptComponent` — ECS system that drives all active `LuaScriptInstance` objects each frame via `on_update(delta_time)`.

## 1.5.5 — Terrain & World

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | `ALandscapeProxy` + World Partition | Heightmap-based terrain with component-based streaming. Virtual texturing for multi-layer materials. Foliage instancing (GPU instanced). World Partition replaces World Composition — grid-based cell streaming with editor support. HLOD for distant geometry. |
| **Godot 4.x** | Community addon (Terrain3D) | No built-in terrain system. Community plugin `Terrain3D` provides heightmap + splatmap + LOD. Basic foliage via `MultiMeshInstance3D`. No world streaming built-in. |
| **Unity 6** | `Terrain` component | Built-in heightmap terrain with splatmap painting. SpeedTree integration for foliage. GPU instancing for grass/trees. Addressable scene loading for world streaming (manual). DOTS Subscenes for streaming. |

**UzEngine**: Heightmap terrain with clipmap LOD. Multi-layer material painting (splatmap). Virtual texturing (tile-based streaming, GPU feedback buffer). GPU instanced foliage (1M+ grass instances target). World partition (grid-based cell streaming, async load/unload). Streaming volumes for manual control.

## 1.5.6 — VFX & Particles

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | Niagara | Modular VFX system. GPU compute for simulation. Emitter → Module stack (spawn, update, render). Data interfaces for external data. Events (collision, death → sub-emitter). Ribbons, mesh particles, light renderers. ~100% node-graph driven. Binary `.uasset` format. |
| **Godot 4.x** | `GPUParticles3D` | Compute shader for simulation. Process material (shader) defines behavior. Limited modularity — each emitter is one process shader. No event system. Trails via `GPUParticlesTrails`. |
| **Unity 6** | VFX Graph (HDRP) / Shuriken (URP) | VFX Graph: node-based, GPU compute, 1M+ particles. Shuriken: CPU-based, older, simpler. Both support ribbons, mesh particles, sub-emitters. VFX Graph stores as `.vfx` (binary). |

**UzEngine**: **Niagara-style modular VFX** but fully open JSON (`.uzvfx`). GPU compute for simulation. Emitter → module stack (spawn, update, render). Forces (gravity, wind, turbulence, noise, vortex). Collision with depth buffer. Ribbons, mesh particles. Events (death → sub-emitter). **AI-first**: every parameter has semantic metadata so LLMs can generate VFX systems from text descriptions.

## 1.5.7 — UI Runtime

### How the Big Engines Solve This

| Engine | Solution | Details |
|--------|----------|---------|
| **Unreal 5.6** | Slate + UMG | Slate: C++ immediate-mode UI framework. UMG (Unreal Motion Graphics): Blueprint-based UI on top of Slate. Widgets, animations, data binding. Rendered to texture, composited as overlay. |
| **Godot 4.x** | Control nodes | `Control` node hierarchy. Built-in widgets (Button, Label, TextEdit). Theme system (JSON). Layout containers (VBox, HBox, Grid). Responsive design. |
| **Unity 6** | UI Toolkit / UGUI | UI Toolkit: HTML/CSS-like (UXML + USS). UGUI: Canvas-based, older. Both render in screen space or world space. Data binding (UI Toolkit). |

**UzEngine**: **Embedded HTML/CSS** with reactive data binding. C++ and Lua expose observable state → UI updates automatically. Standard HTML/CSS for layout/styling (designers don't need engine knowledge). LLMs understand HTML/CSS natively — perfect for AI-generated UI. **imgui** for engine debug overlays (separate from game UI).
