# Spec 1.5.0-SC — Shader Pipeline Architecture

> **Goal**: Robust shader source management, compilation, caching, and hot-reload system that avoids the file-copy and stale-cache problems encountered in POC 1.

---

## Lessons from POC 1

POC 1 exposed two critical failures in shader management:

1. **File references**: Shaders referenced as external `.hlsl` files required copying to the build output. This was fragile — missed copies caused runtime failures, and the build system had no awareness of shader dependencies.

2. **C header embedding**: Converting `.hlsl` to C string headers (`shader.hlsl.h`) solved the copy problem but introduced stale cache bugs. During rapid iteration, the generated headers lagged behind the source, and developers saw old shader behavior with no obvious cause. Cache invalidation was timestamp-based and unreliable across machines.

**Root cause**: Both approaches lacked content-based identity. Without hashing the actual shader source, any caching layer becomes a liability during development.

---

## How the Big Engines Solve This

### Unreal Engine 5.6

**Source management**: Virtual filesystem with directory mappings. `.usf`/`.ush` files loaded from disk via `GShaderSourceDirectoryMappings` — a `TMap<FString, FString>` mapping virtual paths (`/Engine`) to real directories. Plugins register their own shader directories at runtime. No embedding as C strings.

**Cache invalidation**: SHA1 hash of the entire include chain — `GetShaderIncludes()` recursively resolves all `#include` dependencies, feeds every file's content into a hasher. The resulting hash is the cache key. No timestamps. Changing any included file propagates automatically.

**Hot-reload**: Two-level invalidation:
- `InvalidateShaderFileCacheEntry(path)` — surgical, removes one file and its hash
- `FlushShaderFileCache()` — nuclear, clears everything

Editor detects changes via file watcher, invalidates affected entries, resubmits compilation jobs asynchronously.

**Dev vs shipping**: Dev loads `.usf` from disk, compiles on-demand, caches in DDC. Shipping uses `FShaderCodeLibrary` — precompiled `.ushaderbytecode` archives indexed by hash. `LoadShaderSourceFile()` returns false immediately when `RequiresCookedData()` is true.

**Include tracking**: `InternalGetShaderIncludes()` does recursive text-based `#include` parsing. Results cached per root file in `GShaderFileCache`. Flat dependency array with hash table index. Max 200 includes per file.

### Godot 4.x

**Source management**: Build-time embedding via Python codegen. `.glsl` files → `.glsl.gen.h` C++ classes with embedded `const char[]` arrays. Generated class inherits `ShaderRD`, constructor calls `setup()` with the embedded source. User shaders (`.gdshader`) loaded from resource files at runtime.

**Cache invalidation**: SHA-256 content hash over `[version] + [vertex_source] + [fragment_source] + [compute_source] + [debug_flag]`. Per-variant SHA-1 for version-specific parts (uniforms, defines). Cache path: `shader_name / group_sha256 / version_sha1.cache`. Purely content-driven — no timestamps.

**Hot-reload**: Only for user shaders (`.gdshader`), not built-in. Resource change signal system — `ShaderInclude` emits `changed()`, parent shader connects via `connect_changed()`, triggers `_recompile()`. Lazy compilation with `dirty` flag — shader not compiled until `version_get_shader()` is called.

**Dev vs export**: Editor compiles GLSL→SPIRV at runtime with parallel worker threads. Export uses `ShaderBakerExportPlugin` to pre-compile all variants into platform-native bytecode bundled with the game.

**Include tracking**: Two systems — build-time (Python script resolves `#include` recursively with dedup) and runtime (`ShaderIncludeDB` static HashMap for programmatic includes).

## UzEngine Approach

### Design Principles

1. **Content-addressed everything** — xxHash64 of source content is the universal identity. No timestamps, no filenames in cache keys.
2. **Load from disk in dev, archive in ship** — never embed as C strings during development. The stale-header problem is eliminated by not generating headers at all during dev iteration.
3. **Reverse-dependency graph** — when any `.hlsl` file changes, instantly know every shader that needs recompilation.
4. **Lazy + dirty flag** — shaders marked dirty are not recompiled immediately. Compilation happens on next use, allowing batch changes without redundant recompiles.
5. **Zero runtime compilation in shipping** — all bytecode precompiled and archived. Missing shaders are a build error, not a runtime fallback.

### Shader Virtual Filesystem (ShaderVFS)

Inspired by UE5's `GShaderSourceDirectoryMappings`. Each module mounts its shader directory under a virtual path.

```cpp
/// Virtual filesystem for shader source resolution.
/// Maps virtual paths ("/engine/common.hlsli") to real filesystem paths.
/// Modules register mount points at startup — no hardcoded paths.
class ShaderVFS {
    /// Mount a real directory under a virtual prefix.
    /// mount("/engine", "shaders/engine") makes "/engine/pbr.hlsl"
    /// resolve to "shaders/engine/pbr.hlsl".
    void Mount(StringView virtualPrefix, StringView realDir);

    /// Resolve a virtual path to a real filesystem path.
    /// Returns empty if no mount point matches.
    String Resolve(StringView virtualPath) const;

    /// Load shader source from the virtual path.
    /// Returns file contents or empty on failure.
    String LoadSource(StringView virtualPath) const;
};
```

**Why not C header embedding?**
- During development, we edit `.hlsl` files constantly. Embedding creates a code-generation step that must run before compilation, adding latency and a stale-cache surface.
- UE5 proves that loading from disk with content hashing is fast enough — their shader system handles thousands of `.usf` files this way.
- For shipping, we skip the VFS entirely and use a precompiled archive.

### Include Dependency Graph

When a shader is loaded, we parse `#include` directives recursively and build a bidirectional graph:

```cpp
/// Tracks #include dependencies between shader files.
/// Forward graph: "which files does this shader include?"
/// Reverse graph: "which shaders are affected if this file changes?"
class ShaderDependencyGraph {
    /// Parse a shader file, resolve includes, register in graph.
    void RegisterFile(StringView virtualPath);

    /// Get all files transitively included by this shader.
    Span<String> GetDependencies(StringView virtualPath) const;

    /// Get all shaders that transitively depend on this file.
    /// Used for invalidation: if common.hlsli changes, what recompiles?
    Span<String> GetDependents(StringView virtualPath) const;

    /// Remove a file and its edges from the graph.
    void UnregisterFile(StringView virtualPath);
};
```

The graph is rebuilt on startup (fast — just text scanning for `#include`) and updated incrementally when files change.

### Content Hash Identity

Every shader's identity is a single xxHash64 computed from:

```
hash = xxHash64(
    source_content           // the root .hlsl file
  + include_content_sorted   // all transitive includes, sorted by path (deterministic)
  + compile_defines          // permutation flags, e.g. "HAS_NORMAL_MAP=1"
  + target_backend           // "dx12_sm66", "vulkan", "metal"
  + compiler_version         // DXC version string (recompile on DXC update)
)
```

**Why xxHash64 over SHA-256?**
- SHA-256 is ~10x slower and we don't need cryptographic strength
- xxHash64 is already a project dependency
- Cache collisions are astronomically unlikely for our scale

**Why sorted includes?**
- Include order in the hash must be deterministic across machines. Sorting by virtual path ensures the same hash regardless of filesystem enumeration order.

### Shader Cache

```
cache/shaders/
  ├── dx12_sm66/
  │   ├── manifest.json         # hash → {source_path, defines, timestamp_compiled}
  │   ├── a1b2c3d4e5f6.dxil    # compiled DXIL bytecode
  │   └── f6e5d4c3b2a1.dxil
  ├── dx12_sm5/
  │   └── ...
  ├── vulkan/
  │   └── a1b2c3d4e5f6.spv
  └── metal/
      └── a1b2c3d4e5f6.metallib
```

**Cache lookup flow:**
1. Compute xxHash64 of shader + includes + defines + target
2. Check if `cache/shaders/{target}/{hash}.{ext}` exists
3. If yes → load bytecode, skip compilation
4. If no → compile, store result, update manifest

**Manifest** is for debugging only — maps hash back to human-readable info. The hash alone is the cache key; the manifest is never consulted for cache hit/miss decisions.

**Cache invalidation:**
- No explicit invalidation needed. When source changes, the hash changes, and the old cache entry is simply never looked up again.
- Periodic cleanup: delete cache entries not referenced in the current manifest (GC pass).

### Hot-Reload (Dev Builds)

```
FileWatcher (ReadDirectoryChangesW / inotify)
    │
    ▼
ShaderSourceManager::OnFileChanged(realPath)
    │
    ├── Resolve realPath → virtualPath
    ├── Get dependents from ShaderDependencyGraph
    ├── Mark all affected ShaderAssets as dirty
    │   (dirty flag, not immediate recompile)
    ├── Rebuild dependency graph for changed file
    │   (includes may have changed)
    └── Log: "Shader changed: /engine/pbr.hlsl, 3 dependents marked dirty"

Next frame, when renderer calls GetShaderBytecode(handle):
    │
    ├── If not dirty → return cached bytecode (zero cost)
    └── If dirty:
        ├── Recompute hash (source may have changed)
        ├── Check cache (another dev may have compiled it)
        ├── If cache miss → compile synchronously (first frame may hitch)
        │   or async with previous shader until ready
        ├── Update PSO cache (invalidate affected pipelines)
        ├── Clear dirty flag
        └── Log: "Shader recompiled: /engine/pbr.hlsl (12.3ms)"
```

**Why lazy recompile instead of immediate?**
- During rapid iteration, a developer may save multiple times in quick succession (e.g., fixing a typo then changing a value). Lazy recompile only compiles once when the shader is actually needed.
- Godot uses this exact pattern (`Version::dirty` flag) and it works well.

### Permutation System

```hlsl
// In pbr.hlsl:
#pragma uz_permutation HAS_NORMAL_MAP          // bool → 2 variants
#pragma uz_permutation SHADOW_QUALITY LOW MEDIUM HIGH  // enum → 3 variants
// Total: 2 × 3 = 6 variants per backend
```

Each permutation generates a unique `compile_defines` string, which feeds into the hash. The permutation system is orthogonal to the cache — each variant is just another cache entry with a different hash.

**Permutation explosion guard:** max 256 variants per shader. If exceeded, the build system emits an error. This prevents the UE5 problem of tens of thousands of variants.

### Compilation Pipeline

```
                    ┌─────────────┐
                    │ HLSL Source  │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐  ┌────────┐  ┌────────────┐
         │  DXC   │  │  DXC   │  │    DXC     │
         │→ DXIL  │  │→ DXBC  │  │ → SPIR-V   │
         │(SM6.6) │  │(SM5)   │  │ (Vulkan)   │
         └────────┘  └────────┘  └─────┬──────┘
                                       │
                              ┌────────┼────────┐
                              ▼                  ▼
                        ┌──────────┐      ┌──────────┐
                        │SPIRV-Cross│     │SPIRV-Cross│
                        │  → MSL   │     │  → GLSL   │
                        │ (Metal)  │     │(GLES,opt) │
                        └──────────┘     └──────────┘
```

**DXC is loaded dynamically** (`dxcompiler.dll` / `libdxcompiler.so`) — not linked at build time. This allows the engine to run without DXC in shipping builds (where all shaders are precompiled).

### Shipping Build Pipeline

At package time (`uz_build --ship`):

1. Enumerate all `.hlsl` files via ShaderVFS
2. Expand all permutations
3. Compile for target backend(s) — parallel across worker threads
4. Verify 100% cache hit or compile missing shaders
5. Pack all bytecode into `shaders.uzpak` (hash-indexed binary archive)
6. Strip ShaderVFS, FileWatcher, DXC from the shipping binary (`#if UZ_SHADER_DEV`)
7. Build error if any shader fails to compile — never ship with missing shaders

### Post-Switch Compilation

When the user changes `--rhi` or `--shader-model` at startup:

1. Resolve target backend and shader model
2. Scan shader manifest for the new `(backend, sm)` pair
3. If all shaders cached → proceed normally
4. If any missing → compile before first frame:
   - Headless: log progress to console
   - Windowed: display loading screen with progress bar
   - Parallel compilation across all CPU cores
5. Cache results for future runs

This mirrors UE5's DDC model — shaders are compiled lazily per backend and cached by content hash.
