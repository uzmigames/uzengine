# Spec 1.1 — Math & Containers

> **Goal**: Complete math library and core data structures for the rendering and gameplay pipeline.

---

## How the Big Engines Solve This

### Unreal Engine 5.6

**Math**: Custom templated types — `TVector<T>`, `TQuat<T>`, `TMatrix<T>`, `TTransform<T>`. `FVector` / `FVector3d` for float/double. Conditional SIMD via `VectorRegister` (SSE/NEON selected at compile time). **Large World Coordinates (LWC)**: engine-wide double-precision support since UE 5.0 — `FVector` is now `FVector3d` internally, with `FVector3f` for GPU submission. This allows scenes >21km without floating-point jitter.

**AABB/Frustum**: `FBox` (AABB), `FConvexVolume` (frustum). `FConvexVolume::IntersectBox()` for culling. Hierarchical culling with `FOctree2` spatial partitioning.

**Containers**: `TArray<T>` (dynamic array, ~90% of container usage), `TMap<K,V>` (hash map), `TSet<T>`, `TQueue<T>` (lock-free SPSC/MPSC), `TCircularBuffer<T>`, `TBitArray`, `TSparseArray<T>`. Custom allocators per container. `FMemory` backend.

**Allocators**: `FMallocBinned3` (pooled allocator with size classes), `FLinearAllocator`, `FArenaAllocator`. LLM (Low Level Memory) tracker tags every allocation with owner category. Frame allocator cleared each frame for transient data.

**Random**: `FRandomStream` — Mersenne Twister based. `FMath::RandRange()` for simple usage. Seeded streams for deterministic replay.

### Godot 4.x

**Math**: Custom types — `Vector3`, `Basis` (3x3 rotation matrix), `Transform3D`, `Quaternion`, `AABB`, `Plane`. `real_t` typedef allows float/double compile-time switch. **No explicit SIMD** — Godot relies on compiler auto-vectorization (often misses). This is a known performance gap vs Unreal/Unity.

**Containers**: `Vector<T>` (copy-on-write), `HashMap<K,V>` (Robin Hood hashing), `List<T>` (doubly-linked), `RingBuffer<T>`, `LocalVector<T>` (no COW, for perf-critical code). `RID_Owner<T>` — handle-based resource management with generation counters for use-after-free detection.

**Allocators**: `Memory::alloc_static()` / `Memory::free_static()`. Pool allocator for `Object` instances. `PagedAllocator<T>` for bulk allocations. No per-subsystem budget tracking.

**Random**: `RandomPCG` — PCG random number generator. Exposed as `RandomNumberGenerator` in scripting. Seedable for determinism.

### Unity 6

**Math**: `Unity.Mathematics` — `float2`, `float3`, `float4`, `float4x4`, `quaternion`, `RigidTransform`. Shader-like syntax (`math.dot()`, `math.lerp()`). **Burst compiler maps to SIMD automatically** — `float4` operations compile to SSE/AVX instructions. No manual SIMD needed.

**Containers**: `NativeArray<T>`, `NativeList<T>`, `NativeHashMap<K,V>` — unmanaged, Burst-compatible. Safety system checks for read/write access in debug builds (similar to our borrow checker idea). `UnsafeList<T>` for no-safety-check paths.

**Allocators**: `Allocator.Temp` (frame-scoped), `Allocator.TempJob` (job-scoped, 4 frames), `Allocator.Persistent` (manual free). Memory is tracked per allocation type. `UnsafeUtility.Malloc/Free` for raw allocation.

**Random**: `Unity.Mathematics.Random` — xorshift128. Seeded, deterministic. Compatible with Burst jobs.

## The Problem

The math and container layer sits between the foundation and every other subsystem. It must be:

1. **SIMD by default** — not "optional SIMD" like Godot where you hope the compiler vectorizes. Every Vec3/Vec4/Mat4 operation must use SIMD instructions.
2. **Cache-friendly** — containers used in hot loops (ECS iteration, render submission) must be contiguous in memory
3. **Safe in debug, fast in release** — use-after-free, double-borrow, out-of-bounds must be caught in development but stripped in shipping
4. **Allocation-aware** — every container and math operation must use our allocator infrastructure, never global `new`
5. **LWC-ready** — large world coordinates need double-precision position with float-precision relative math (camera-relative rendering)

Unreal solves this best but with enormous template complexity. Unity's Burst+Mathematics is elegant but needs a managed runtime. Godot is the weakest here — no SIMD, copy-on-write containers.

## UzEngine Approach

### Math Library
**DirectXMath + thin ergonomic wrapper.**

We're DX12-first — DirectXMath is the native math lib with zero impedance mismatch to the GPU. Every operation is SIMD (SSE2 baseline, SSE4/AVX2 with runtime dispatch).

```cpp
// Thin wrapper over DirectXMath XMVECTOR/XMMATRIX
struct Vec3 {
    XMVECTOR v;  // Always in SIMD register
    Vec3 operator+(Vec3 b) const { return { XMVectorAdd(v, b.v) }; }
    float X() const { return XMVectorGetX(v); }
    // ...
};

struct Mat4 {
    XMMATRIX m;
    static Mat4 Perspective(float fov, float aspect, float near, float far);
    static Mat4 LookAt(Vec3 eye, Vec3 target, Vec3 up);
    Vec3 TransformPoint(Vec3 p) const;
};

struct Quat {
    XMVECTOR q;
    static Quat FromEuler(float pitch, float yaw, float roll);
    Vec3 RotateVector(Vec3 v) const;
    Quat Slerp(Quat target, float t) const;
};

struct Transform {
    Vec3 position;
    Quat rotation;
    Vec3 scale;
    Mat4 ToMatrix() const;
};
```

**Why not custom from scratch**: DirectXMath is battle-tested in thousands of games, header-only, MIT, SIMD by default. Writing our own SIMD math from scratch would be slower to develop and buggier. The thin wrapper gives us clean API while DirectXMath does the heavy lifting.

**SIMD validation**: Release builds must show SSE4/AVX2 instructions in disassembly for all math ops. CI check with `objdump` to verify.

### Containers

| Container | Purpose | Analog |
|-----------|---------|--------|
| `RingBuffer<T>` | Lock-free SPSC queue (render command submission) | Unreal `TCircularBuffer` |
| `FreeList<T>` | O(1) alloc/free from pool, no fragmentation | Custom |
| `HandleMap<T>` | Generational handle → pointer, safe resource lookup | Godot `RID_Owner` |
| `FrameArray<T>` | Per-frame scratch array, reset each frame | Unreal's frame allocator pattern |

**HandleMap** is critical for safe resource management:

```cpp
HandleMap<Texture> textures;
Handle<Texture> h = textures.Create(desc);  // Returns typed handle
Texture* ptr = textures.Get(h);             // O(1) lookup, nullptr if stale
textures.Destroy(h);                         // Invalidates handle
textures.Get(h);                             // Returns nullptr (generation mismatch)
```

Generation counter prevents use-after-free — same slot can be reused but old handles are invalid. This is how Godot's RID system works, and how our RHI resources will be managed.

### Allocators

| Allocator | Pattern | Use Case |
|-----------|---------|----------|
| `LinearAllocator` | Bump pointer, reset to start | Frame-scoped scratch data |
| `PoolAllocator<T>` | Fixed-size blocks, free list | Component pools, particles |
| `FrameAllocator` | Linear, auto-reset each frame | Transient render data, command lists |

All allocators are named and tracked:

```cpp
auto* alloc = PoolAllocator<Particle>::Create("VFX.Particles", 1024);
// Memory usage queryable per allocator name
```

### Random

**PCG (Permuted Congruential Generator)** — same as Godot. Fast, statistically excellent, small state (128-bit), seedable for deterministic replay.

```cpp
PCGRandom rng(seed);
float f = rng.Float();           // [0, 1)
float r = rng.Range(0.0f, 1.0f); // [min, max)
int i = rng.Int(0, 100);         // [min, max]
Vec3 dir = rng.UnitSphere();     // Random direction on unit sphere
```
