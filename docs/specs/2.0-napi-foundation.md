# Spec 2.0 — N-API Foundation

> **Goal**: Runtime compiled as native N-API addon, loaded in-process by VSCode extension host. Extension scaffold, lifecycle management, shared GPU surface for viewport.
>
> **POC 0.2 Status**: Partially validated — DX12 render + H.264 MF encode + WebCodecs decode = 120 FPS at 854x480 with 50K instances.

---

## How the Big Engines Solve This (Editor Embedding)

### Unreal Engine 5.6

**Architecture**: Monolithic. Editor IS the engine — same executable, same process. `UEditorEngine` subclasses `UEngine`. Editor modules loaded at startup, stripped in shipping builds. The viewport is a native OS window managed by Slate (Unreal's UI framework).

**Pros**: Zero communication overhead. Full access to all engine internals. No serialization between editor and runtime.
**Cons**: Massive binary (4-5 GB). Can't use a lightweight editor. Editor crash = engine crash. Not embeddable in other tools.

### Godot 4.x

**Architecture**: Monolithic (like Unreal). The Godot editor is built with the engine's own UI system (`Control` nodes). Same executable — `godot.editor` vs `godot.runtime` are just different build configs. Viewport is a native Vulkan/D3D12/Metal surface.

**Pros**: Same as Unreal — zero overhead, full access.
**Cons**: Same as Unreal — not embeddable, tightly coupled.

### Unity 6

**Architecture**: Separate processes. Editor (C#, managed) communicates with the native engine runtime via internal IPC. The Game View is a render texture displayed in the editor. Play mode runs in-process but with a domain reload (~3-5s). Build produces a standalone executable separate from the editor.

**Pros**: Editor can be written in managed code (faster UI iteration). Build artifacts are clean standalone binaries.
**Cons**: Domain reload is slow. Play mode has different behavior than standalone. Editor→Runtime communication has overhead.

### VSCode Extensions (typical)

Most tools that integrate native code with VSCode use **separate processes** with IPC (Language Server Protocol, WebSocket, stdin/stdout). Examples: Rust Analyzer (LSP), Live Share (custom protocol), C++ Intellisense (LSP).

**Why we don't do this**: POC 0.1 proved that IPC is a hard bottleneck for frame streaming (244 FPS render → 60 FPS display). A game engine needs zero-overhead communication between editor and runtime.

## The Problem

We're doing something no other engine does — embedding a full native C++ runtime inside a VSCode extension process. This requires solving:

1. **ABI compatibility** — the `.node` addon must match Electron's Node.js ABI exactly
2. **Crash isolation** — addon crash kills the extension host (Electron restarts it in ~1s), which is acceptable but must produce diagnostics
3. **Viewport rendering** — the main 3D viewport needs a native OS window with a DX12 swapchain (not a webview)
4. **Frame streaming for webview panels** — preview panels, remote headless, etc. need H.264 streaming
5. **Lifecycle** — start/stop runtime cleanly from extension activation/deactivation

## UzEngine Approach — Validated by POC 0.2

### N-API Addon Compilation

```
napi/
├── CMakeLists.txt          # cmake-js config
├── package.json            # node-addon-api + cmake-js
└── src/
    ├── addon.cpp           # N-API bindings
    └── ...                 # Links runtime C++ code
```

**Critical requirements** (discovered in POC 0.2):
- `${CMAKE_JS_SRC}` **MUST** be in CMakeLists — delay-load hook for Electron (without it, `require()` segfaults on Windows)
- `NAPI_DISABLE_CPP_EXCEPTIONS` — NAPI_CPP_EXCEPTIONS crashes Electron (electron#22799)
- `--runtime=electron --runtime-version=<ver>` — must match Electron's Node ABI
- Current: VSCode 1.111.0 = Electron 39.6.0 / Node 22.22.0 / ABI 140

### Viewport: Native HWND (NOT webview)

The 3D viewport is a **native borderless window** created by the runtime, positioned over VSCode:

```
┌─ VSCode Window ─────────────────────────────────┐
│  ┌─ Viewport (native HWND, DX12 swapchain) ──┐  │
│  │                                              │  │
│  │        Direct DX12 presentation              │  │
│  │        Zero readback, zero encoding          │  │
│  │        Mouse/keyboard captured directly      │  │
│  │                                              │  │
│  └──────────────────────────────────────────────┘  │
│  ┌─ Inspector (webview) ┐  ┌─ Hierarchy (webview)┐│
│  │  HTML/CSS editor UI   │  │  HTML/CSS tree view  ││
│  └───────────────────────┘  └─────────────────────┘│
└────────────────────────────────────────────────────┘
```

**Why**: Shared GPU surface = zero transfer overhead. The viewport renders at display refresh rate. No readback, no H.264 encode/decode, no postMessage. This is how Unreal/Godot do it — the viewport IS a native GPU surface.

**Challenge**: Positioning a native HWND inside VSCode requires tracking the webview panel's position/size and updating the HWND accordingly. The extension will provide panel geometry via N-API, and the runtime will `SetWindowPos()` the viewport.

**Fallback**: If native HWND embedding proves unreliable, fall back to H.264 streaming (proven at 120 FPS in POC 0.2).

### Frame Streaming (for webview panels)

For non-viewport panels (preview, remote headless), use the proven H.264 pipeline:

```
C++ (runtime thread)          Extension Host (Node.js)        Webview
─────────────────────         ──────────────────────         ──────────
DX12 render
  → GPU readback (RGBA)
  → MF H.264 HW encode
  → triple-buffer slot
                              renderFrame() via N-API
                              → Buffer + keyframe flag
                              → postMessage to webview
                                                              → WebCodecs VideoDecoder
                                                              → VideoFrame
                                                              → canvas.drawImage()
                                                                 or TrackGenerator → <video>
```

- **Encode**: Media Foundation H.264 (hardware ASIC), Baseline profile, 20Mbps CBR, GOP=15, 0 B-frames, low-latency mode
- **Decode**: WebCodecs `VideoDecoder` (`avc1.42001e`, `optimizeForLatency: true`)
- **Display**: Canvas drawImage (fallback) or MediaStreamTrackGenerator → `<video>` (native compositor)
- **Transport**: Node Buffer via `postMessage`
- **Result**: 120 FPS sustained at 854x480 with 50K spinning cubes

### Extension Scaffold

```typescript
// extension.ts
import * as vscode from 'vscode';

export function activate(context: vscode.ExtensionContext) {
    const addon = require('./build/Release/uzengine.node');

    // Register commands
    context.subscriptions.push(
        vscode.commands.registerCommand('uzengine.openViewport', () => {
            addon.createViewport(/* HWND parent info */);
        }),
        vscode.commands.registerCommand('uzengine.openScene', (uri) => {
            addon.loadScene(uri.fsPath);
        })
    );
}

export function deactivate() {
    // addon.shutdown() — cleanup DX12, MF, physics, etc.
}
```

### Lifecycle Management

| Event | Action |
|-------|--------|
| Extension activate | `require('.node')` → start pool manager → pre-warm idle runtimes |
| Open scene tab | Pool assigns pre-warmed runtime → loads scene → renders in <500ms |
| Close scene tab | Runtime releases scene → returns to idle pool (or destroyed if above max) |
| Open viewport | Runtime creates native HWND, bind swapchain, start render loop |
| Close viewport | Destroy HWND, release swapchain |
| Extension deactivate | `--pool-shutdown` → all runtimes flush GPU + release resources → binary unlocked |
| Extension host crash | Electron restarts host (~1s). Runtimes create minidump before death. |
| Recompile | Build script calls `--pool-shutdown` first → waits for exit → compiles → extension restarts pool |

### Runtime Pool (POC 0.1 Lesson)

**Problem discovered in POC 0.1**: As the engine grew, opening a scene took several seconds (DX12 device creation, subsystem init, asset loading). Users opening multiple scene tabs in VSCode experienced unacceptable latency. Additionally, **recompiling the runtime while pool processes were running caused link errors** (`EBUSY` / file locked) — a constant friction during development.

**Solution**: Pre-warmed runtime pool.

```
Extension activates
  → Pool manager starts
  → Spawns N idle runtimes (DX12 device + subsystems initialized, NO scene loaded)
  → User opens "level1.uzscene"
    → Pool assigns Runtime 0 → sends scene path → loads in <500ms
    → Pool spawns replacement idle runtime to maintain min_warm
  → User opens "level2.uzscene"
    → Pool assigns Runtime 1 → loads scene
  → User recompiles (Ctrl+Shift+B)
    → Build hook calls --pool-shutdown
    → All runtimes gracefully exit (GPU flush, resource release)
    → Binary unlocked → compile succeeds
    → Extension restarts pool automatically
```

**CLI interface**:
```bash
uzengine-runtime --pool --min-warm 2 --max-total 8   # Start pool
uzengine-runtime --pool-shutdown                       # Kill pool (before recompile)
uzengine-runtime --scene "path.uzscene" --no-pool      # Standalone (debug/CI)
```

**Pool manager lives inside the runtime binary** (not a separate app) — invoked with `--pool` flag. This avoids having two binaries to compile and manage. The pool manager is a lightweight coordinator that spawns child runtime instances.

**Build-safe teardown**: The extension registers a `preBuild` task in `.vscode/tasks.json` that calls `--pool-shutdown` before any compile step. This eliminates the `EBUSY` file-lock problem that was a constant pain in POC 0.1.

**In-process vs child process**: With N-API, the pool can manage multiple runtime instances **within the same extension host process** (each with own DX12 device and scene state). If this proves unstable (one crash kills all), fall back to child processes with IPC bridge. The native HWND viewport works either way.
