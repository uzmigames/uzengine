# Proposal: phase1-ecs-spatial-query

## Why

NPC AI, physics triggers, and rendering culling all need to answer "which entities are near this point?" or "which entities overlap this volume?" at runtime. Without a spatial index, every such query requires a linear scan of all entities with a `CTransform` component — O(N) per query, per frame. At 500 entities this is tolerable; at 2000 entities running 10 AI queries per frame it accounts for 20,000 AABB tests per frame that should cost 20 log-N lookups instead. Enemies scanning for the nearest player, trigger volumes firing when the player enters, and the renderer culling draw calls against the camera frustum all share this pattern and all pay the same O(N) tax without a spatial structure.

A BVH (Bounding Volume Hierarchy) built over entity AABBs provides O(log N) sphere overlap, AABB overlap, frustum overlap, and ray intersection queries. Crucially, the BVH must stay coherent with the ECS without requiring manual notification — entities that move, appear, or are destroyed must be reflected in the index within the same frame, so AI scripts and physics triggers see a consistent spatial snapshot every tick.

The Lua API surface must be simple enough for a game scripter to use without understanding the BVH internals: `ctx.world:query_sphere(pos, radius, tag)` returns a list of entity handles, mirroring the idiom of Unity's `Physics.OverlapSphere` and Unreal's `UKismetSystemLibrary::SphereOverlapActors`. This familiarity lowers the learning curve while the underlying C++ implementation delivers engine-grade performance.

## What Changes

- Define `SpatialIndex` abstract interface in `src/engine/ecs/SpatialIndex.h` with pure-virtual methods: `void insert(entt::entity, AABB)`, `void update(entt::entity, AABB)`, `void remove(entt::entity)`, `void query_sphere(float3 center, float radius, std::vector<entt::entity>& out)`, `void query_aabb(AABB, std::vector<entt::entity>& out)`, `void query_frustum(Frustum, std::vector<entt::entity>& out)`, `bool raycast(float3 origin, float3 dir, float max_dist, RaycastHit& out)`
- Implement `BvhSpatialIndex` in `src/engine/ecs/BvhSpatialIndex.cpp`: surface-area-heuristic (SAH) top-down build, incremental refit on `update()`, full rebuild triggered when dirty-node count exceeds 20% of total node count; internal nodes use `float3 min, max` AABB pairs stored in a flat `std::vector<BvhNode>` for cache-friendly traversal; leaf nodes store `entt::entity` + AABB
- Add `SpatialIndexSystem` ECS system in `src/engine/ecs/SpatialIndexSystem.h/cpp`: use EnTT `registry.on_construct<CTransform>()`, `registry.on_update<CTransform>()`, and `registry.on_destroy<CTransform>()` observers to queue dirty entities; at the start of each frame's update tick, flush the dirty queue into `BvhSpatialIndex` with batched `insert`/`update`/`remove` calls before any AI or script code runs; expose the current `SpatialIndex*` pointer on the `World` singleton so other systems can query it
- Compute the per-entity AABB used for insertion: if the entity has a `CMeshRenderer`, use the mesh's pre-computed world-space AABB transformed by `CTransform::world_matrix`; if it has only a `CTransform`, use a point-AABB (min == max == translation); store the last inserted AABB in a parallel `std::unordered_map<entt::entity, AABB>` to detect whether a transform change actually moved the AABB enough to warrant an update (threshold: 0.001 world units)
- Implement tag filtering at the query layer: each query method accepts an optional `uint64_t tag_mask` parameter matching the CTags bitset from the tags-groups system; entities that do not have all requested bits set in their `CTags` component are excluded from the result list without traversing their subtree in the BVH (the BVH node stores the union of all child tag bits, allowing subtree early-out when the query mask has zero overlap with the union)
- Add Lua bindings in `src/engine/scripting/lua_world.cpp`: `ctx.world:query_sphere(center_vec3, radius, optional_tag_name) -> NodeRef[]`, `ctx.world:query_aabb(min_vec3, max_vec3, optional_tag_name) -> NodeRef[]`, `ctx.world:raycast(origin_vec3, dir_vec3, max_dist) -> RaycastHit | nil` where `RaycastHit` is a Lua table with fields `entity` (NodeRef), `point` (vec3), `normal` (vec3), `distance` (number); all queries run on the main thread and return results immediately (no async API)
- Expose the BVH to the renderer frustum culler: `RendererSystem::cull_draw_calls()` calls `SpatialIndex::query_frustum(camera_frustum, visible_entities)` instead of its current linear scan over all `CMeshRenderer` components, replacing approximately 80 lines of brute-force loop code with a single BVH query
- Add `SpatialIndex` rebuild statistics to the debug profiler: `spatial.query_count`, `spatial.dirty_node_count`, `spatial.bvh_depth`, `spatial.last_rebuild_ms` reported as named counters visible in the debug overlay and accessible via `ctx.debug:get_counter(name)` from Lua
- Write unit tests in `tests/engine/spatial_index_test.cpp` covering: BVH correctness after batch insert (all inserted entities returned by full-scene sphere query), sphere query excludes entities outside radius, AABB query with tag mask returns only matching entities, raycast returns nearest hit when two entities overlap the ray, incremental update moves entity correctly without full rebuild, entity removal is reflected within the same frame

## Impact

- Affected specs: `docs/specs/scene-system.md` (spatial query API section), `docs/specs/tags-groups.md` (tag-mask parameter on query methods), `docs/specs/renderer.md` (frustum culling uses BVH), `docs/specs/debug-profiling.md` (BVH statistics counters), `docs/specs/lua-scripting.md` (ctx.world query and raycast API)
- Affected code: `src/engine/ecs/SpatialIndex.h` (new), `src/engine/ecs/BvhSpatialIndex.cpp` (new), `src/engine/ecs/SpatialIndexSystem.h/cpp` (new), `src/engine/scripting/lua_world.cpp` (query/raycast bindings), `src/renderer/RendererSystem.cpp` (frustum cull uses BVH), `tests/engine/spatial_index_test.cpp` (new)
- Breaking change: NO — additive; existing scene code, EnTT registry usage, and Lua scripts are unaffected; the BVH is a new parallel data structure that observes existing component changes passively
- User benefit: NPC "find nearest enemy" queries and trigger volume checks run in O(log N) instead of O(N), making scenes with 1000+ entities feasible without frame budget spikes; game scripts gain a simple three-function spatial API identical in feel to Unity/Unreal, requiring no knowledge of the underlying BVH
