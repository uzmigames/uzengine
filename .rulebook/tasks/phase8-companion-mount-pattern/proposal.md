# Proposal: phase3-companion-mount-pattern

## Why

Pets and mounts are nearly universal in MMO games. Every player in the world can have an active pet following them, and in towns or gathering areas, it is common to see 50+ players simultaneously with their active pets and mounts. The rendering and AI costs of companion entities are expected and handled by the existing skeletal mesh and AI systems. What is not obvious to engine newcomers — and what causes a disproportionate number of MMO-specific bugs — is the physics collision behavior of companions.

In Unreal Engine, a pet pawn spawned with a standard capsule collider will collide with the player's capsule, the ground, NPCs, other pets, and environmental geometry. The result is a classic MMO bug: pets get stuck in doorways, they push players sideways when walking, they stack on top of each other in crowded areas, they block projectiles, and they register as obstacles for pathfinding. Every MMO built on UE4 has had to manually suppress physics collision on companion pawns as an early fix. It is such a known issue that community forums have documented the `SetCollisionEnabled(NoCollision)` fix for companion pawns.

The second problem with companion physics is performance. In a crowded town with 100 players each having 2 active companions, that is 200 physics bodies in the simulation that serve no gameplay purpose. Jolt Physics can handle 200 simple bodies, but multiply that by collision contacts with environment geometry, other bodies, and you have 200 extra bodies contributing to broad-phase and narrow-phase calculations every frame for zero gameplay value.

UzEngine must make the correct behavior the default: companion entities do not have physics bodies. The `CCompanion` component signals to the physics system to skip body creation. The COMPANION collision layer is excluded from all standard query layers. Owner interaction is handled via owner tag comparison, not physics contacts.

## What Changes

- **`src/engine/components/companion.h`**: New component. Defines `CCompanion { owner_id: EntityId, type: CompanionType, allow_collision_with_owner: bool }`. `CompanionType` enum: `PET=0, MOUNT=1, SUMMON=2, FAMILIAR=3`. `allow_collision_with_owner` defaults to `false`; set `true` only for `MOUNT` type where the player must stand on the mount's back.
- **`src/engine/systems/physics_system.cpp`**: In `PhysicsSystem::register_entity(EntityId)`, add early-return check: `if (ecs.has<CCompanion>(id)) { LOG_DEBUG("CCompanion entity {} — no physics body created", id); return; }`. This prevents any `CCollider` shapes from being registered to Jolt for companion entities, regardless of what other components are present.
- **`src/asset/validation/entity_validator.cpp`**: Add validation rule: if entity has both `CCompanion` and `CCollider` (or `CRigidBody`), emit warning `W_COMPANION_HAS_COLLIDER`. Warning text: "CCompanion entity has CCollider. This is almost always unintentional. Companion entities should have no collision geometry. Add suppress: companion_collision_warning to CCompanion to suppress." The warning is configurable per-entity via `CCompanion.suppress_warnings: ["companion_collision_warning"]`.
- **Collision layer setup**: Add `COMPANION = 0x0040` to the physics collision layer enum. The default layer matrix configures `COMPANION` to collide with nothing (empty `collides_with` list). When `allow_collision_with_owner: true` (for mounts), a temporary contact pair is created at runtime between the specific mount entity and its owner's `PLAYER` layer body — not a global layer-vs-layer rule.
- **`src/engine/systems/companion_follow_system.cpp`**: New file. Handles companion movement: reads `CFollowAI { target: EntityId, follow_radius: float, offset: float3 }` and updates `CTransform` to follow the target. Since companions have no physics body, position is set directly on `CTransform` each frame, not via physics impulses. Uses simple lerp with configurable smoothing. Does not use navmesh by default (pets teleport through walls rather than navigating around them, which is a visual-only entity and acceptable behavior).
- **Owner-only interaction**: Interaction events from a `CCompanion` entity are only dispatched to entities where `entity.id == companion.owner_id`. Implemented in the event bus dispatch for `interaction.begin` events: if the interacting entity has `CCompanion`, filter receivers to `owner_id` only.
- **Lua API**: `ctx.entity:is_companion(entity_id) -> bool`, `ctx.companion:get_owner(entity_id) -> EntityId`, `ctx.companion:set_follow_target(entity_id, target_id)`, `ctx.companion:detach(entity_id)`.
- **`.uzscene` documentation**: Document the companion entity pattern with a full example snippet (skeletal mesh + CFollowAI + CCompanion, explicitly without CCollider/CRigidBody).
- **Tests**: Unit test: spawn a `CCompanion` entity with a `CCollider` component. Verify `PhysicsSystem::register_entity` skips body creation and logs the expected debug message. Verify that the entity validator emits `W_COMPANION_HAS_COLLIDER`. Integration test: spawn 100 `CCompanion` PET entities around a player entity. Verify Jolt body count remains at the pre-spawn count (no new bodies). Verify `companion_follow_system` correctly positions all 100 companions within follow radius of their respective owners each frame.
- **Documentation**: Create `docs/specs/gameplay/companion-mount-pattern.md`. Update `docs/specs/engine/optimization-systems.md` section 9. Update `docs/specs/physics/physics-system.md` with the COMPANION layer exclusion.

## Impact

- **Affected specs**: `docs/specs/physics/physics-system.md`, `docs/specs/engine/optimization-systems.md`
- **Affected code**: `src/engine/components/companion.h` (new), `src/engine/systems/physics_system.cpp`, `src/engine/systems/companion_follow_system.cpp` (new), `src/asset/validation/entity_validator.cpp`, `src/ipc/handlers/entity_handlers.cpp`
- **Breaking change**: NO — additive component. Existing entities are unaffected. `CCompanion` entities with pre-existing `CCollider` components will now have those colliders silently ignored by the physics system and will receive a validation warning.
- **User benefit**: Zero physics bugs for pet and mount entities by default. Companion entities cost zero physics simulation time. Towns with 50+ players each having 2 active companions do not add 100+ physics bodies to the simulation. The documented pattern prevents an entire class of MMO-specific physics bugs from ever being introduced.
