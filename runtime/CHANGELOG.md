| v0.9.14 | 2026-04-25 | **D3D12MA shutdown leak fix — `FontAtlas` + `MsdfFontAtlas` (2 MiB) released, engine exits with code 0**. Hardware bring-up exposed that `uzengine.exe --diag --frames 60` consistently tripped D3D12MA's `m_pMetadata->IsEmpty()` assertion at process exit even after the mesh-module leak fix shipped earlier today. The named-allocation diagnostic at `dx12_device.cpp:88-131` was using `UZ_LOG(RHI, Warning, ...)` whose async file sink could be dropped between the queue and the flush when the assertion's `abort()` killed the process — the log file would only contain unrelated init-time errors and never the leak dump. **Diagnostic fix**: switched the leak dump to `std::fprintf(stderr, ...)` + `std::fflush(stderr)` so it bypasses spdlog's async pipeline and survives `abort()`. The output now reads `[D3D12MA-LEAK] N live allocations` followed by per-heap stats and per-buffer / per-texture name + size dumps. **Root-cause fix**: the leak dump revealed exactly 2 leaked allocations on the DEFAULT heap — `FontAtlas` (1024x1024 R8, 1 MiB) and `MsdfFontAtlas` (1024x1024 R8, 1 MiB), both owned by `VfxEditorOverlay`. The overlay's `Shutdown()` only called `m_textRenderer.Shutdown()` and ignored `m_font` and `m_msdfFont`; both font classes ship explicit `Shutdown(IRHIDevice*)` methods that destroy their atlas textures, but they were never invoked. Changed the overlay's `Shutdown()` signature to accept an `IRHIDevice*` (single call site at `scene_renderer_init.cpp:1609` updated to pass `m_device`) and call the font shutdowns. **Result**: `uzengine.exe --diag --frames 60` -> ExitCode 0, STDERR 0 bytes, 60 frames rendered, 20 render targets reporting (16 OK + 4 WARN_ZERO from missing scene content), no D3D12MA assertion.
